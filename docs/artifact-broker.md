# Protected artifact and package broker

The host authority loads `/etc/hermes-installer/artifact-catalog.json` as a protected installer-owned mode-0600 file and builds fixed handlers with staging root `/var/lib/hermes-installer/artifacts`. The catalog and staging directories must not be writable by profiles or other untrusted principals. `load_protected_catalog` rejects symlinked/non-regular files, unsafe ownership or mode, duplicate JSON keys, unknown fields, unsupported URLs, invalid digests, and invalid bounds. The authority process must run as its enrolled installer UID.

A caller sends only `artifact_id`, catalog SHA-256 and `max_bytes`; it cannot choose a URL or path. The handler binds those fields to the signed one-use grant, checks cancellation and the monotonic lease, revalidates the current authority policy immediately before opening the network connection, and checks cancellation/deadline again. It fetches from the catalog HTTPS URL with certificate verification, no inherited proxy, and catalog-allowlisted redirect hosts, then verifies stream size and digest. Interrupted transfers keep a private partial file and resume only while the grant remains live. Completed bytes are fsynced and atomically renamed to a content-addressed, read-only file. The receipt contains an opaque `artifact:<id>:<sha256>` store ID, digest and size; it contains no bytes, URL, credential or filesystem path.

`ArtifactCatalog.resolve_store_id(store_id, staging_root, expected_uid=0)` resolves only that enrolled object after checking ownership, regular-file type, write bits, byte limits and a fresh SHA-256. `materialize_store_id(...)` additionally extracts an enrolled archive into a protected immutable tree and compares every path, digest, size, executable bit and enrolled symlink target. Tar gzip and tar xz archives are supported. Absolute, escaping, cyclic, dangling, special-file, or parent-symlink-conflicting entries are rejected. The result exposes `path`, `sha256`, `tree_files` and a canonical `tree_manifest_sha256`; caller-side work should use a private writable copy when a build tool needs to edit source.

The reviewed seed catalog pins the Hermes installer at source commit `7085fbf7753266fc4943c55ac04926186bc90005`, that commit's PM lock, and the PM-declared Linux ARM64 Python 3.14.7, uv 0.12.3 and Node 26.7.0 artifacts. It also includes the exact Colibri source archive and the reviewed Coral CPython 3.9.25 source, TFLite 2.14.0 and NumPy 1.26.4 wheels, official compiled sample model, and Coral inference worker source. Archive rows contain complete per-file manifests; direct wheels, worker and model bytes remain separately digest-pinned. These rows authorize only fixed-ID retrieval/materialization, not successful runtime installation, component operation, or hardware qualification. The Coral Python 3.9 source is EOL, and the target's native ABI/delegate requirements still gate enablement.

The full Hermes source pin is separately identified as `hermes-source-7085fbf7753266fc4943c55ac04926186bc90005` (80,347,460-byte archive, SHA-256 `592ac0b09a7130cf2f8166f039098ba4ed40fb91535c601a6a7e5b1fcf889d01`). `materialize_pinned_hermes_source` accepts only its opaque store ID, checks the exact catalog tree and normalization manifest, streams the archive once into a private temporary tree, verifies each file digest/mode and reconstructs the upstream Git tree SHA-1 before atomically publishing an immutable root-owned tree. The official archive exports exactly 37 PowerShell files with CRLF; only those listed files are normalized for Git-object reconstruction, with raw archive bytes and hashes retained. `PinnedHermesSourceProvisioner` calls the fixed `BootstrapCustody.fetch_artifact` operation for this one catalog row, verifies its returned store ID and effect receipt, then calls `register_pinned_hermes_source_receipt`. The root setup operation accepts this provisioner as `source_receipt_provider` and calls it only after independent setup admission succeeds. `register_pinned_hermes_source_receipt` mints a random setup-scoped root receipt only after archive and tree verification succeed. The resulting `HermesSourceReceiptHandoff.source` carries root-private paths; only `receipt_handle` may be serialized to the first-snapshot enrollment request. This handler must be explicitly supplied when the root-local setup endpoint is assembled; no production endpoint assembly or Pi acceptance is established by these adapters and fixtures.

Legacy Python package records refer to one specific ZIP wheelhouse, runtime identity, protected interpreter and versioned installation root. Their manifest allows only exact `name==version` requirements carrying SHA-256 hashes. Coral uses a separate signed root-protected `/etc/hermes-installer/package-sets.json` enrollment. Its fixed `coral-cp39-runtime-v1` set binds the enrolled CPython 3.9.25 build/executable attestation, service identity and venv root to exactly the protected TFLite 2.14.0 and NumPy 1.26.4 wheel IDs. The caller supplies only package-set ID, enrollment ID and generation; the effect target binds the protected manifest digest. The root handler verifies artifact bytes and ARM64 wheel metadata, then invokes only the enrolled interpreter with fixed offline venv/pip commands, `--no-index`, `--no-deps`, `--only-binary` and `--require-hashes`. Installation runs in a root-created network namespace, with sanitized environment, bounded cancellation/reap, immutable versioned staging and an installed-tree receipt. It exposes no arbitrary shell, caller-supplied commands, package-index access, paths, or wheelhouse construction. The protected manifest and runtime enrollment must be created only after the target CPython runtime has been built and attested; neither this adapter nor its fixtures establish target runtime or TPU acceptance.

Artifact catalog JSON uses schema 1 with exact top-level keys `schema`, `artifacts`, and `packages`. Artifact rows have `artifact_id`, `version`, `sha256`, `source_url`, `max_bytes`, `size_bytes`, `redirect_hosts`, `filename`, `tree_files`, `archive_format`, `archive_root`, and `max_tree_bytes`. Tree rows contain `path`, `sha256`, `size_bytes`, `executable`, `kind`, and `link_target`; legacy regular-file rows with the original four fields remain accepted. `archive_root` is null or an exact normalized tar directory prefix ending in `/`. Legacy package rows have `package_id`, `version`, `artifact_id`, `artifact_sha256`, `runtime_id`, `python_executable`, `environment_root`, and `install_timeout_seconds`. Package-set JSON has schema 1 and a `package_sets` array whose records are signed over canonical JSON by the enrolled host key and then protected by root ownership/mode. The protected catalog file limit is 16 MiB to accommodate reviewed complete file manifests.

Implementation evidence is covered by OpenSpec `host-principal-custody` HI01/HI-T01 and `installer-bootstrap-desktop` BD-F01, with lifecycle recovery LC-F01 as a prerequisite. The catalog remains inert until root daemon assembly enrolls the fixed catalog/staging paths and passes the root-only policy revalidation callback; no live target has been installed or accepted by this adapter.
