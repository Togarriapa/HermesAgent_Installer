# Protected artifact and package broker

The host authority loads `/etc/hermes-installer/artifact-catalog.json` as a protected root-owned file and builds the fixed handlers with the staging root `/var/lib/hermes-installer/artifacts`. The catalog and staging directories must not be writable by profiles or other untrusted principals. `load_protected_catalog` rejects symlinked/non-regular files, writable catalog files/directories, duplicate JSON keys, unknown fields, unsupported URLs, invalid digests, and invalid bounds. The authority process must run as the enrolled installer UID.

The root-side caller sends only `artifact_id`, the catalog SHA-256 and `max_bytes`. The handler binds those fields to the signed one-use grant, fetches from the catalog HTTPS URL with certificate verification, no inherited proxy, and catalog allowlisted redirect hosts, then verifies the stream's size and digest. Interrupted transfers keep a private partial file and resume with a validated byte range. A completed artifact is written by fsync plus atomic rename to a content-addressed, read-only file. The receipt contains an opaque `artifact:<id>:<sha256>` store ID, digest and size; it contains no bytes, URL, credential or filesystem path.

`ArtifactCatalog.resolve(id, sha256, root)` resolves only that enrolled object after checking ownership, regular-file type, write bits, byte limits and a fresh SHA-256. For enrolled archives, `materialize_tree(id, sha256, root)` additionally rejects links and special files, enforces the expansion/file-count bounds, compares every extracted path and digest with the protected `tree_files`, and atomically publishes a read-only tree. This is the API the protected custody loader should use when pinning interpreter scripts or other child artifacts. It never accepts a profile-selected path.

Python package records refer to a specific ZIP wheelhouse, runtime identity, protected interpreter and versioned installation root. The manifest allows only exact `name==version` requirements carrying SHA-256 hashes. Installation runs a fixed `python -m venv --copies` command followed by offline pip with `--no-index`, `--no-deps`, `--only-binary`, and `--require-hashes`; it uses a sanitized environment and bounded process-group cancellation. No source builds, package-index access, arbitrary shell, caller-supplied command, or lazy dependency download is available through this handler. A package whose exact wheelhouse or runtime is not enrolled stays unavailable with `artifact.enrollment` or `artifact.missing`; the caller can resume by requesting the same catalog artifact identity after fixing the reported condition.

Catalog JSON uses schema 1 with exact top-level keys `schema`, `artifacts`, and `packages`. Artifact rows have `artifact_id`, `version`, `sha256`, `source_url`, `max_bytes`, `size_bytes`, `redirect_hosts`, `filename`, `tree_files`, `archive_format`, `archive_root`, and `max_tree_bytes`. `archive_root` is null or an exact normalized top-level prefix ending in `/`; it is supported only for tar.gz and every member must be beneath that enrolled prefix. Each `tree_files` item has `path`, `sha256`, `size_bytes`, and `executable` (a boolean; only cataloged files receive execute bits). Package rows have `package_id`, `version`, `artifact_id`, `artifact_sha256`, `runtime_id`, `python_executable`, `environment_root`, and `install_timeout_seconds`. Source revisions alone do not populate this operational catalog: each artifact row still needs an exact downloadable digest/size and, for archives, an exact content tree reviewed by the source owner.

Implementation evidence is covered by OpenSpec `host-principal-custody` HI01/HI-T01 and `installer-bootstrap-desktop` BD-F01, with lifecycle recovery LC-F01 as a prerequisite. The catalog remains inert until the root daemon assembly enrolls the fixed paths and handler mapping; no live target has been installed or accepted by this adapter.
