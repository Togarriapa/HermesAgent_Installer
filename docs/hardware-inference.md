# Colibri GLM-5.2 and Coral inference

The Colibri and Coral paths are separate. Coral accelerates compatible fully quantized TensorFlow Lite models; it does not accelerate GLM/Colibri. The request remains the exact MIT-tagged GLM-5.2 package `mastouri/GLM-5.2-colibri-int4-g64-with-int8-mtp` at revision `6bbb01ed3e515a8730b694dfae73aadfd6774581`. The reviewed inventory is 149 files totaling 429,276,220,139 bytes. Upstream's separate `usedStorage` claim is 429,276,080,522 bytes; capacity planning uses the larger exact sum of the selected files.

## GLM-5.2 selection and installation

The manifest reader is `hermes_installer.models.artifacts.ArtifactManifest.from_metadata`. It rejects a different model/revision, missing MTP artifact, altered inventory, missing checksum, or changed upstream size claim. Each artifact is verified using its actual published checksum type: SHA-256 for LFS objects and Git's typed blob SHA-1 for ordinary files. There is no fallback model.

Before the user selects the model, call `estimate_storage(manifest, selected_path, reserve)` and display download, final, conversion temporary, rollback, and system reserve bytes. `StorageReserve` must include the operator's measured OS, Hermes, user-data, cache, log, and recovery needs. The estimate holds one model-sized staging area plus any configured conversion temporary space and old generation for rollback; it does not create a generic second model backup. A selected existing model path can be checked with `verify_existing_model` in place. No copy is needed.

After explicit model selection and sufficient space, `download_generation` writes pinned shards to `.stage-<manifest fingerprint>`. Re-running it resumes partial files with HTTP Range requests. A server that ignores Range triggers a safe restart; a malformed `Content-Range`, digest mismatch, overlong response, cancellation, or ENOSPC never activates an incomplete generation. Interrupted prefixes remain available for resume. When all files verify, the completed generation is renamed into place; `activate_generation` verifies every artifact and ownership marker before atomically swapping the `current` symlink. An operator-owned non-symlink `current` path or unowned generation is preserved and reported.

The selected C engine is `JustVugg/colibri` commit `bf2442915d6e3dd4cdfd2eb9c2a3d2aa44a25850` (Apache-2.0), enrolled as the official 11,412,458-byte archive with SHA-256 `7cc79d4bfdc851efb27b67295ceac1370312b5cd414d869887715d30b2d13174`. `request_colibri_arm64_build` selects only the fixed root-enrolled build operation; it has no caller source path, compiler argv, or environment input. Its result parser requires the root terminal-build receipt to bind the pinned source, selected service generation, output path/role, ELF64 AArch64/Linux facts, target instruction policy, and actual hashed libgomp/libm/libc dependency closure. The matching Coral CPython operation requires root-observed 3.9.25/SOABI/nondebug/ARM64 facts, actual glibc >=2.34, and the complete native-extension closure. Receipt parsing is not build execution: the protected terminal runner, root receipt registration, and independent Linux target qualification are still required, so both component operations remain unavailable until those host APIs are composed. The exact pinned Colibri source does not contain optional `c/glm_tiny`; no self-test success is fabricated. A request for Colibri service is denied unless the host manager attests memory, CPU, I/O, lifetime, cleanup, and health bounds. The API binds only to `127.0.0.1:8000`; its API key is a protected credential reference injected by the service manager and never an argv value. Cancelling a generation stops the managed service because the pinned Colibri server has no per-request cancellation endpoint.

Run `run_glm_benchmark_workflow` only against a fresh managed Colibri service and the selected generation, with the host `ServiceConnectorClient` and exact enrollment/generation/session. The benchmark adapter sends only fixed `POST /v1/chat/completions` requests through the connector's approved `colibri-openai-v1` route; it validates the host generation and stream bounds, applies byte/deadline caps, decodes bounded HTTP chunk framing, and closes the stream on every path. It does not open the service's namespace-local loopback directly or permit caller paths, headers, or URLs. The connector currently supplies an opaque byte stream, so it does not provide a health endpoint; the first inference request is the functional API check. The workflow measures one cold request, five configurable-by-policy or more warm tool-call trials, prompt/completion token accounting, first-token latency, generated tokens per second, resident memory, throttling before/after each request, and direct read-only fio throughput on a verified selected shard. Core-chat latency is measured while fio reads that shard. Tool behavior passes only when the model emits `benchmark_add` with valid `{"a":1,"b":2}` arguments. Default thresholds are configurable: warm first token at most 30 seconds, at least 1 generated token/second, and core-chat p95 at most 10 seconds. The verifier does not promote results unless it is actually running on native ARM64 with matching hostname and `/etc/machine-id`; missing throttling, memory, token accounting, tool output, target, or auxiliary responsiveness keeps the report pending or experimental. Save reports with `save_report` as local evidence; they do not prove a Pi measurement until collected on the authorized Pi.

## Coral runtime and hardware qualification

Use `probe_coral_devices` and `choose_coral_device` to identify USB (`18d1:9302`) or PCIe (`1ac1:089a`) devices and reject ambiguous or inaccessible hardware. `runtime_plan` reports the official `libedgetpu1-std` package, plus `gasket-dkms` for PCIe, and isolated ARM64 CPython build requirements. `provision_coral_device` uses the supplied managed package installer; PCIe driver installation returns `pending_reboot` and never reboots automatically. Device permission must be scoped by root custody to the exact selected USB character node or selected PCIe `/dev/apex_0`; the component does not grant access by editing broad group membership. The selected identity includes resolved sysfs path, device-node major/minor and inode. There is not yet a landed root device-binding effect that can expose exactly that node under `PrivateDevices`, so Coral worker activation remains unavailable.

The worker uses the official compiled quantized sample from `google-coral/test_data` commit `104342d2d3480b3e66203073dac24f4e2dbb4c41`: `mobilenet_v2_1.0_224_quant_edgetpu.tflite`, 4,283,046 bytes, SHA-256 `4315ee115507aab28c78809c0f384e5296527dd6a5dd53a1751b3eb9c91db6aa` (Apache-2.0). `download_official_sample(..., selected=True)` copies only the exact protected artifact-catalog receipt, rechecks its hash and size, and publishes it without overwriting an existing destination. The worker creates a quantized zero-input execution fixture, explicitly loads the Edge TPU delegate for one selected transport, invokes the model, and requires at least one `DELEGATE` operation plus a hashed output. This demonstrates execution only; it is not classification-accuracy evidence. CPU fallback, delegate-load-only, hardware enumeration, or an unrelated model cannot qualify.

Coral's currently available official Python stack requires legacy CPython 3.9. The pins in `planning/coral-component-runtime-metadata.json` are CPython 3.9.25 source (20,183,236 bytes; SHA-256 `00e07d7c0f2f0cc002432d1ee84d2a40dae404a99303e3f97701c10966c91834`), TFLite Runtime 2.14.0 CPython 3.9 ARM64/glibc 2.34+ wheel (2,325,666 bytes; SHA-256 `be198b7dc4401204be54a15884d9e336389790eb707439524540f5a9329fdd02`), and NumPy 1.26.4 CPython 3.9 ARM64 wheel (14,226,281 bytes; SHA-256 `d5241e0a80d808d70546c697135da2c613f30e28251ff8307eb72ba696945764`). The protected catalog resolves these exact source/wheel receipts. The typed package-set caller sends only the selected enrollment, generation, package-set ID and protected manifest digest, and accepts a root receipt bound to the exact wheels and installed tree. `request_coral_cpython_build` selects only the fixed CPython source-build recipe and accepts only the corresponding root terminal receipt and ABI facts. The authority daemon has not registered the terminal build handler or package-set factory, and neither an attested isolated runtime nor its target installation is qualified. Python 3.9 reached end of life on 2025-10-31; this compatibility path is legacy and not presented as a current supported production stack. It never alters Hermes PM Python 3.14 or the host default Python.

The worker must run under the installer host's dedicated identity with verified filesystem/process/credential isolation, a closed network namespace, only the selected TPU device node exposed, and bounded manager cleanup. Only the manager can provide those guarantees. The worker requires the generation-bound selection digest from the root-authenticated device enrollment/result, and the assessment adapter compares it with that host result alongside the official sample, runtime digest, compatible runtime, delegate load and use, delegated operation count, completed inference, and output digest. A local sysfs observation digest is not a substitute for the root selection digest. The current host caller does not yet provide a verified selection receipt, so Coral inference remains unavailable. A fake delegate fixture in unit tests checks rejection behavior only; it is not live hardware evidence.

## Evidence status

The repository contains the source and artifact pins, storage/download/activation logic, build and runtime adapters, benchmark collector, and contract tests. Development did not build Colibri, provision Coral packages/Python, download GLM-5.2, or execute inference on the Pi. The official small Coral artifact pin was checked, but real USB/PCIe delegate-used inference remains pending. GLM-5.2 storage acceptance and cold/warm performance also remain pending until the exact 429 GB package is user-selected, capacity is sufficient, the bounded manager and account/runtime prerequisites pass, and measurements are recorded on the authorized native Pi. A hardware inventory or fixture result is not that acceptance.

## Root-enrolled devices and native builds

`hermes_installer.protected_enrollment.ProtectedDeviceCatalog` resolves an opaque device ID and generation to one root-enrolled USB physical path or PCI BDF, exact sysfs identity, device-node major/minor/inode, vendor/product IDs, and (for PCIe) the expected driver. Each resolution re-reads the current sysfs/node identity; removal, re-enumeration, path reuse, a changed driver, or a stale generation rejects before the device can be admitted. The resulting `char-M:m:rwm` rule is a selector for a host device policy, not proof that a private device namespace or cgroup rule has been installed. Never replace it with an all-USB or all-apex allowance.


`ProtectedBuildCatalog` recognizes only `coral-cpython-build:start` and `colibri-source-build:start`. Each protected record binds exact source, toolchain and builder artifact IDs/digests, fixed argv/environment, output root ID and owner, deadline, and required output digests. Output attestation checks an owner-scoped staging tree beneath root-protected ancestors and rejects symlinked or substituted outputs. `ProtectedEnrollmentCatalog.resolve_package_runtime` joins the Coral CPython package set to the exact build generation and output attestation, verifies the actual target glibc and executable digest, and returns only root-resolved runtime/venv paths for the protected package broker. These catalog and attestation APIs are now present with fixtures, but their Linux build sandbox, root authority registration and native target qualification remain pending; no compiler was run on the development Mac and no Pi build/device result is claimed. Keep both operations unavailable until the root service has registered these records, isolated the unprivileged builder with network and runtime credentials denied, and qualified exact device and output binding on the identified Linux target.
