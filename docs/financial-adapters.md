# Financial Plugin adapters

The pinned `agent-live-wallet`, `agent-sandbox-wallet`, `financial-data-hub`, and `financial-execution-gateway` declarations are represented by typed adapters in `src/hermes_installer/components/plugin_finance.py`. The adapters register fixed Hermes tools and require a separately enrolled root-owned runtime service for every financial effect. YAML capabilities, imported profile prompts, account labels, and caller-supplied URLs never grant that service.

`FinancialDataHub` accepts one opaque read credential reference and one opaque account reference per selected provider. Its operation catalog matches each provider's read scopes; it refuses writes before dispatch, bounds filters and replies, and removes account and credential fields before returning provenance-bearing observations.

Wallet instances receive opaque vault and RPC service references, exact network IDs, chain IDs, and asset allowlists from enrollment. The sandbox accepts only Sepolia or Solana Devnet enrollments and denies mainnet bridging and non-test assets. Live wallet signing and broadcasting require an invocation-bound root confirmation for the exact normalized transaction. The adapter cannot read or export key material.

`FinancialExecutionGateway` binds provider, enrolled account, operation, and canonical action digest. Root preflight checks current account state and supported simulation or fees before `consume_financial_confirmation` consumes a fresh one-shot confirmation with a maximum five-minute lifetime. The only provider effect is the root broker's single-use `execute_once` call. `SQLiteExecutionLedger` persistently claims each order, rejects replay, redacts receipts, and records ambiguous or reconciliation-failed states. Ambiguous results require the explicit `reconcile_ambiguous` path and never trigger a second submission.

The contract tests use fixture brokers and signer/verifier doubles to prove positive calls, denials before side effects, replay handling, response redaction, and ambiguous-result recovery. They do not prove that a bank, broker, exchange, RPC, encrypted vault, wallet, Ledger device, or native Hermes account is enrolled or operational. Live execution, mainnet key creation, signing, broadcast, and account mutation remain unavailable until the host AuthorityService supplies the reviewed protected interfaces and the user separately enrolls the exact accounts/networks/assets. No real transaction or provider write was performed for these tests.
