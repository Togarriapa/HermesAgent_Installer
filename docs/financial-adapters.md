# Financial Plugin adapters

The pinned `agent-live-wallet`, `agent-sandbox-wallet`, `financial-data-hub`, and `financial-execution-gateway` declarations are represented by typed Hermes tools in `src/hermes_installer/components/plugin_finance.py`. Every production handler crosses only `runtime_context.plugin_effects.invoke`; no injected client/service, network URL, credential, key, signer, arbitrary command, or profile value can perform an effect. The root broker resolves accounts, recipients, network targets, credentials, vault references, lineage, budgets, and final-payload confirmation from protected enrollment.

The root action IDs are fixed: `plugin.financial-data-hub.read`, `plugin.financial-execution-gateway.execute`, `plugin.agent-live-wallet.read` / `.execute`, and `plugin.agent-sandbox-wallet.read` / `.execute`. Data provider/operation pairs are filtered by the vendored read-only catalog before dispatch. Execution takes provider, operation, and bounded exact action data; it does not accept an account or payment recipient. Wallet calls take an enrolled network label and bounded action, never an RPC endpoint. Sandbox is limited to Sepolia and Solana Devnet, and writes must state `test_asset=true` and `mainnet_bridge=false`.

Each mutating invocation requires a bounded opaque confirmation-attestation handle supplied separately from the final arguments. The adapter derives a stable idempotency key from the adapter, fixed action ID, canonical arguments, and attestation handle. Root Authority must resolve the account/target, bind a fresh trusted human order to the exact final payload and target generation, and atomically consume the one-shot attestation. Plugin deployment/selection does not authorize a transaction. Pending or ambiguous results stay pending/ambiguous and are never reported as successful; the adapter does not retry. Reconciliation and durable effect/idempotency records belong to the root dispatcher.

The fixtures prove the registered tools call the root facade with the fixed operation IDs, exclude caller-selected account/confirmation fields from arguments, reject missing/malformed confirmation and sandbox bridge claims, redact sensitive result fields, and preserve ambiguous state. They do not prove that any provider, account, vault, signer, wallet, financial target, or native account is enrolled or operational. No real transaction, provider write, live funds, or outbound message was used. Native account acceptance and root target enrollment remain pending.
