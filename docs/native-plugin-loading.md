# Native Hermes package loader

The native package loader is a worker-side consumer of the protected HI08/HI09 package binder. It accepts no package ID, generation, profile path, mount path, resolver file, module path, or environment override from a caller. The root binder selects the active package for the authenticated process and generation; the only mount target is derived from the package/profile/generation/compiled-closure digest tuple in `planning/protected-runtime-assembly-contract.json`.

The implementation requires the expected private read-only mount with `ro,nosuid,nodev,noexec`, validates the strict UTF-8 manifest and complete `closure/` file set, verifies each file’s digest, size and mode, and joins all manifest adapter/action rows to the root-selected resolver. The native assembly entrypoint-manifest SHA, source resource-manifest SHA, adapter-module SHA, closure-tree SHA, and resolver-document SHA remain distinct pins. It rejects unlisted files, symlinks, hard links, special files, duplicate/case-colliding paths, malformed rows, stale binding leases, and resolver/manifest drift before importing an adapter. It does not search user plugins, user site-packages, `PYTHONPATH`, or other mount locations.

`SelectedNativePackage.resolve()` is presentation metadata. A row never authorizes an effect. Registered adapters must receive a trusted runtime context with a host-derived invocation lineage provider and the typed `plugin_effects` facade. Root effect admission must re-resolve enrollment, generation, schema, source closure and operation for each call. The selected-package binder and mount verifier are implemented, but the root has not yet composed a response observer/current invocation-context API or a root-observed loader-ready/action event. Native registration and source-sensitive effects therefore remain unavailable. Worker-submitted SDK bodies remain unknown/private and are not proof of user-interface ingress.

The loader reads each selected adapter module directly from its verified closure path and does not add that closure to `sys.path` or discover adapter modules from profile directories. It also refuses startup when `PYTHONPATH`/`PYTHONHOME` are set or the interpreter has user-site imports enabled. This is not a Python sandbox or a complete import-confinement mechanism: Python imports performed by adapter code still use the already-configured Hermes runtime environment. The runtime must continue to use its protected, sanitized environment, and native effects must remain behind the root broker.

Fixture tests cover the pinned manifest and closure validator, fixed mount derivation, resolver-to-mount digest binding, mount-flag failures and adapter entrypoint shape. They do not prove a root-created namespace mount, the protected custody recipe, an authenticated user ingress, a root-observed loader-ready event, or native target acceptance.
