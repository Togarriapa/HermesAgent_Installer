# Root policy generation publication

`authority.setup_policy_publication.RootSetupPolicyGenerationPublisher` is the filesystem owner for initial and active compiler publications. A typed one-use compiler claim supplies exact compiled bytes; this module does not accept policy bytes, release roots, file rows, or receipt metadata from a worker call. `publish(handle, expected_selection_catalog_sha256)` validates the current sealed release and claim, stages the exact compiled policy and catalog in a new immutable generation, records the root journal receipt, and atomically publishes `/etc/hermes-installer/root-setup-selection.json` last.

The first publication uses `expected_selection_catalog_sha256=None` only when the fixed selection is absent. Later compare-and-swap uses the actual current catalog digest. Concurrent changes, unsafe ownership, links, unexpected generation content, or a mismatched journal fail without replacing an existing selection. The journal retains the selected generation identity and the source receipt handles so root-side receipt registries can resolve their full evidence closure.

`PolicyPublicationReceiptResolver.resolve_current()` independently checks the current selection against its journal record and immutable generation descriptor and files. Prepared empty policy records remain prepared. Active promotion requires a separate typed claim bound to the normal setup session and actual runnable-custody receipts. Its digest-only choice projections retain the signed row and payload digests, signer/release identity, purpose, source receipt closure, principal/profile/namespace selectors and binding digests, choice and revocation epochs, prepared generation, service generation, and compiled selection digest. The publisher seals these projections to the committed publication receipt and stores them in both the immutable descriptor and protected journal. `PublishedSetupChoiceAdoption.verify_current()` resolves only the currently selected active generation. The choice registry separately rechecks the original signed row and current source/selector state before adopting it; that adoption does not itself grant runtime permission. Active publication rollback/CAS failure cannot issue an adoption receipt. Functional qualification and final health remain separate.

The fixed installed-release verifier is in `authority.installer_release`. The repository does not yet define a sealed installer candidate source/build receipt for its deployment writer, so no arbitrary source path or caller-supplied manifest is accepted here. A root deployment producer must be wired to that reviewed candidate input before a fresh installation can create the fixed deployment receipt.
