# Root consent registries

Private provider egress and automatic memory capture use separate root-owned preferences. Both default to absent. `RootTTYConsentChoiceRegistry` first presents the finite profiles in the committed active root enrollment, then presents only the selected profile's protected private provider routes or separately selected memory engine and capture routes on the foreground controlling TTY. Blank input clears the current profile and both choices; blank route selection clears that purpose's choice. Every persisted choice records the root controller and TTY identity, exact profile/service generations, and policy revision/digest. Prepared enrollments, the unrelated Resources profile prompt, worker configuration, sensitivity labels, and public-route availability cannot create consent.

`RootPrivateInputConsentRegistry` stores a profile's finite private provider route and recipient selection with additional metered budget fixed at zero. `selection_handle_for_current_profile(binding)` returns only an opaque preference handle for the actual current `PrincipalBinding`. For each selected input, `resolve_for_selected_input(...)` checks the exact root-retained source observation and `RootSelectedNativeExecution`, current profile selection, enrolled routes, policy, parent recipient ceilings, and revocation epoch. It mints a signed receipt capped at 30 seconds and at the shorter input/execution lease. The source observation is still consumed by the normal source issuer; consent resolution does not turn the proof into a source receipt.

At dispatch, retry, or background-child boundaries, `revalidate_retained_input_consent(...)` checks the saved root receipt and exact retained selection handle against current consent, route, policy, profile, and execution state. It returns the same in-memory receipt object with its original expiry. It does not consume the proof, mint a replacement, widen recipients, or refresh an expired lease. Revocation durably advances the profile consent epoch, so an earlier receipt stops resolving as current.

`RootMemoryCaptureConsentRegistry` stores a separate explicit opt-in bound to one selected memory owner, provider engine, service generation, and finite private capture routes. That preference is not the completed turn, a `BackgroundConsent`, or an effect grant. Each capture resolution additionally requires the actual retained completed-turn receipt and the exact active immutable `MemoryServiceEnrollment`. Revocation advances the persisted epoch; queued work must recheck currentness before each effect and discard pending payloads under the existing memory ledger rules. Neither registry claims to erase already committed backend memory.

The protected JSON stores are under the selected root journal, owner-only, no-follow, atomically replaced, and signed with the host authority key. Registry signatures are integrity evidence, not independent bearer authorization: consumers must resolve the current registry entry and its retained input/turn bindings. TTY choices and consent records retain identifiers and policy digests only; they do not store transcripts, prompts, source payloads, or secrets.

These APIs establish installer implementation behavior only. They do not prove that an enrolled Pi, external account, or memory backend is active or functional. Native process and target acceptance remain separately gated by their existing evidence.
