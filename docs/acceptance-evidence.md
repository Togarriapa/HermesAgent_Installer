# Acceptance evidence and readiness

The installer records each result against one immutable candidate Git SHA. The report aggregator trusts no JSON row by itself: an enrolled verifier must authenticate the retained evidence artifact. Without that verification, even a syntactically valid prepopulated `pass` remains untrusted and acceptance stays pending. `fixture`, `native-arm64`, `physical-pi`, and `account` evidence are separate lanes. Source selection, download, configuration, discovery, and inventory can describe progress, but they never establish functional acceptance. A skipped or unimplemented workflow remains pending. A failure remains visible and prevents a green report.

`hermes-installer verify --target <authorized-target.json> --output <evidence-dir>` is the current CLI shape. The CLI still reports pending until its target enrollment and functional probes are integrated. `TargetWorkflowRunner` revalidates target fields and expiry at use, checks the selected acceptance scope, and requires the configured enrollment authority before dispatch. A missing registered workflow performs no target effect.

For the Pi Connect owner-run path, `verification.operator_evidence.ProbeRequest` defines a versioned request with the exact candidate and target, authorization reference and manifest digest, direct `argv` (never a shell string), working directory, environment-variable name allowlist, deadline, stdout/stderr byte limits, and stable expected assertion IDs. Request values may not contain credentials; environment values are never part of the request. The owner executes only the command they reviewed on the authorized Pi and returns a structured result with request/candidate/target/command/cwd digests, UTC start/end, exit status, output byte counts and SHA-256 digests, per-assertion outcomes (`true`, `false`, or `null` for not observed), and stable effect IDs. Raw stdout/stderr and environment values are not accepted in result JSON. Truncated output, mismatched bindings, exceeded deadlines/limits, missing assertions, or failed effects cannot pass. An observed false assertion or nonzero exit is a failure; a null assertion remains pending and retains the exact observations made; only complete all-true observations can be a probe pass.

The accepted assertion set is selected by the installer-owned `verification.profiles` registry for the exact acceptance/evidence ID pair. A request cannot replace a missing native, authorization, or negative-proof criterion with a caller-chosen `true` assertion. Its evidence class is derived from the target platform (`fixture-x86_64`, `linux-arm64`, or `raspberry-pi-5-arm64`) and mismatches are rejected. These rules validate the shape and scope of an observation; they do not make an operator's booleans self-authenticating or show that the named command actually ran. The enrolled verifier must inspect and authenticate the exact retained bundle and target provenance. Account-lane proofs remain separate: this Pi command collector does not create Cloudflare/account evidence, and a successful Pi record cannot satisfy the account half of AC13–AC15 or AC17.

`verify_operator_result(request, result, authorized_target)` performs structural and binding checks; `VerifiedProbe.retain(OwnedRoot(...))` stores the exact canonical request/result bundle privately and only then emits an `EvidenceRecord` whose artifact digest covers those retained bytes. This is an observation record, not an automatic trust decision. Report aggregation still requires the enrolled verifier to authenticate the exact retained artifact. Test fixtures must use the `fixture` evidence class; fixture evidence can never satisfy the physical-Pi/account acceptance requirements.

`TargetWorkflowRunner.run()` returns pending without target effects when its explicitly supplied workflow mapping has no entry for the acceptance ID. A registered callback's record must match the full candidate SHA, target identity, platform-derived evidence lane, and exact installer-owned evidence/assertion profile. A callback's structurally complete `pass` remains pending at the workflow boundary until `acceptance_report()` authenticates the retained artifact with the enrolled verifier. The production CLI currently has no registered functional target workflows and truthfully reports pending.

The verification API now exposes `build_fixed_workflows(checkout, candidate_sha)`, which registers only AC16's local EV-RB01 probe. It verifies the candidate checkout, loads the checksum-verified bundled Resources source, performs native discovery/crosswalk/materialization through the installer-owned registry APIs, and retains a deterministic summary under a private `OwnedRoot`. This is a local package/materialization observation; it does not contact a target, activate a resource, or invoke a Hermes profile. The returned observation is still pending enrolled-verifier authentication, and it does not satisfy AC16's remaining EV-RB evidence. Other acceptance IDs intentionally have no fixed functional adapter yet. The CLI remains pending until target enrollment and authentication are composed with these adapter registrations.

Each evidence record binds an evidence ID to the full candidate SHA, platform, target identity where applicable, UTC start/end, a redacted command summary, exit code, observed assertion IDs, and digest of the retained artifact. The generated report lists every traceable requirement separately from its implementation state and evidence state, and reports fixture, native ARM64, physical Pi, and account lanes independently. A trusted pass requires exit code zero, nonempty all-true observations, a retained artifact digest, and an enrolled verifier decision for that artifact. Reports serialize only an allow-listed record shape and redact token-like fields and values. Do not place credentials, access tokens, raw logs, environment values, or private prompt content in evidence.

`load_acceptance_catalog(planning_dir)` combines AC01–AC15 from `planning/traceability.json` with AC16–AC18 from the append-only Resources, Access-read, and host-custody amendment manifests. It carries each amendment's requirement, task, and evidence IDs into the report and rejects missing or duplicate acceptance IDs. AC16 covers the self-contained Resources bundle and real native materialization; AC17 covers fresh Access policy membership and bounded revocation evidence; AC18 covers root-owned host custody, kernel-enforced worker isolation, and mandatory native dispatch mediation. AC13–AC15 and AC17 require both target and account evidence; the other workflows require physical Pi evidence. AC18 additionally needs the separate native isolation observations in its EV-HI evidence set.
