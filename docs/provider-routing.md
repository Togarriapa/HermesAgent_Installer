# Provider routing and account eligibility

Provider use is opt-in and fails closed. The default additional metered budget is zero. A model catalog, the `:free` suffix, source configuration, or a credential reference does not establish account entitlement or effective account privacy settings.

## Dispatch boundary

All managed provider requests use the shared Dispatcher. It normalizes the model, token bound, plugins, tool schema and provider routing fields before transport. Unsupported modalities and provider-side tools are rejected. Routes have exact model allowlists, maximum sensitivity, capability and known price fields. Unknown prices and private work without an eligible private route are unavailable. Paid calls require a deliberately configured positive aggregate budget, reserve spend before the network request, reconcile usage conservatively, and keep reservations for ambiguous failures.

The production dispatcher requires the host AuthorityClient. It accepts a host-signed context bound to the local peer UID, principal, profile, namespace, purpose, intent, trace, verified source lineage, sensitivity, policy revision and monotonic lease. Caller labels cannot promote protected or unclassified data. The dispatcher derives inference versus tool-call capability from the canonical JSON body, hashes the final normalized payload, and obtains and locally verifies a fresh one-use grant for each retry. Each grant binds the exact enrolled target ID, recipient, payload digest and zero-based retry index. It then passes the bytes only through the root-owned `provider.dispatch` broker verb, which independently verifies and consumes the grant, checks the payload semantics and performs bounded TLS egress. Direct provider HTTP from the worker is disabled. Missing issuer, broker, protected profile-purpose enrollment or eligible route leaves inference unavailable.

Retries are bounded, cancellation-aware and deadline-limited. Retry-After is clamped. Fallback routes are explicit policy entries and must satisfy the same model, sensitivity, capability, price and budget checks. Provider-side fallback, plugins, compression and unreviewed transforms are disabled in the public OpenRouter request.

## OpenRouter Nemotron

The pinned public route is `nvidia/nemotron-3-ultra-550b-a55b:free` at the fixed OpenRouter endpoint. The adapter requires current authoritative account-policy evidence before resolving the key or opening a network client. Evidence binds the model, private credential reference, credential fingerprint, account-policy snapshot and expiry. Synthetic eligibility evidence is accepted only by opted-in test fixtures. The fixed root handler factory now binds exact target/recipient, principal, model, credential scope, payload digest, retry and sensitivity, then requires a fresh protected admission immediately before egress. Production still has no configured account admission or host-vault enrollment, so the service does not register this handler and OpenRouter inference remains unavailable until account, model, zero-price, endpoint and effective processing-policy eligibility are proven.

The host target identity is `provider://openrouter/api/v1/chat/completions?model=nvidia%2Fnemotron-3-ultra-550b-a55b%3Afree`; it is an enrolled broker identifier, never a caller-supplied URL. The public route accepts text and ordinary function tools only. Image/audio/video inputs, server-side tools, response-format modes, caller-selected plugins, model overrides and fallback lists are rejected. OpenRouter currently lists the free variant at $0 input/output, 1M context, and 65,536 maximum completion tokens; it supports function `tools` and `tool_choice`, but not `response_format`. The endpoint says not to submit confidential or personal data and describes usage logging for NVIDIA service improvement. Catalog pricing and model support do not prove account entitlement or account-specific privacy settings ([model entry](https://openrouter.ai/nvidia/nemotron-3-ultra-550b-a55b:free)). Do not send private Google or Home Assistant content, private repositories, personal memory, tool results, system context or derived summaries to this route.

## Codex and Claude

Codex subscription sign-in and separately billed OpenAI API keys are distinct. `openai_auth.ChatGPTPlanAuth` implements the public-client Sign in with ChatGPT code+PKCE flow behind injected host-brokered HTTP, ID-token verification and host-vault interfaces. It binds a stable host ID and per-account issued client ID, checks state/nonce/audience/issuer/subject and requires the returned `chatgpt.tokens.use.direct` scope before storing credentials in the injected vault. Refresh is serialized per account and retains rotating token pairs together. Sign-out discovers and validates the issuer's revocation endpoint, attempts refresh-token revocation, clears local tokens, and keeps the account/client mapping; its result distinguishes confirmed remote revocation from local-only sign-out. It never writes OAuth tokens into Hermes profiles. This is functional OAuth contract code; no account has been enrolled here.

The provider branch now has a bounded `CodexResponsesTransport` contract for the documented Responses wire format ([OpenAI Sign in with ChatGPT: Codex App Server](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)). It validates the exact normalized payload digest against the signed host context, derives inference versus tool-call capability from the canonical body, and accepts only a typed authority verification receipt bound to the exact one-use grant. A provider retry requires a fresh context and grant with unchanged principal, profile, namespace, source closure, and payload binding; it never silently reuses the initial context. It submits only text and declared function schemas through the fixed host broker target `codex://responses`; the broker must resolve the account token from its protected vault and send only to OpenAI’s official `/v1/responses` endpoint. The adapter does not receive a token or URL, and it rejects stored/background/streaming responses, multimodal input, and provider-side tools. A fixed root `provider_effect_handlers.build_provider_handlers()` adapter and synthetic handler contract test are present, but the authority daemon still needs an enrolled account record, root vault scope and live eligibility admission before it registers a production handler. It is not yet wired into Hermes’ native dispatcher. Do not replay subscription credentials through a fabricated OpenAI-compatible Chat Completions API. Inference remains unavailable until the host broker handler and account are enrolled, the installed Hermes version exposes a reviewed path, and a no-cost account-specific canary succeeds. OpenAI API keys remain a separate, metered route requiring an explicitly configured aggregate budget.

Keep Claude Free in the account inventory. Current Claude Code documentation lists paid plans and other named eligibility paths, not the consumer Free tier ([Claude Code authentication](https://code.claude.com/docs/en/authentication)). A consumer login alone does not prove Claude Code, Anthropic API, or third-party inference eligibility. If a supported account path cannot be verified, automatic Claude inference is unavailable. Do not extract browser cookies or bridge the consumer web session to an API.

## OmniRoute

OmniRoute is not a verified installed service in this repository state. Its upstream runtime requires Node.js 22.22.2 or newer within the 22 line, or 24 or newer within the 24 line; the Pi system Node 20.19 does not qualify. Before enabling it, use a separately managed runtime, verify the pinned source and ARM64 dependency path, then configure an explicit provider allowlist and bounded loopback service. Do not accept its advertised free-provider list as account proof or allow proxy defaults to bypass route policy. Until the service path and recording-endpoint failure fixtures pass on supported ARM64, keep it pending and use a direct verified provider adapter only where policy permits.

## Evidence status

Contract fixtures demonstrate policy behavior against synthetic transports and synthetic account proof. They do not establish external account entitlement, live provider terms, actual account-level privacy settings, host process/filesystem isolation, or live Pi inference. Account, model, provider service, and target acceptance must be recorded separately with fresh evidence. No user credential or external account is enrolled by this code.
