# Managed lifecycle and recovery

The installer keeps its journal and locks under the private installer state root. Application files live under the separately owned data root: immutable candidate generations in `generations/`, profile state in `profiles/`, and user-owned overlays and memories in `overlays/` and `memory/`. Generation manifests record file digests. A candidate becomes active only after its health check passes; activation updates one fsynced pointer, and rollback switches that pointer to the previously recorded healthy generation.

`GenerationStore` provides the typed staging, activation, status, and rollback effects. `LifecycleRecovery` creates versioned data backups, restores only into the owned data root by default, and removes only generation directories whose ownership records and markers match. Backups preserve profiles, overlays, memories, configuration, and selected user data. Credential values in `.env`, token, credential, secret, and auth files are excluded; references remain references to the configured secure store. Backup and restore operations checkpoint their exact private staging directory before creating it. On the next backup or restore, interrupted staging is removed only when its name matches that operation's recorded UUID, the directory is owned by the current user, and its mode is private; symlinks, foreign-owned paths, and malformed names are left untouched. A backup whose final rename completed before power loss is recovered only after its versioned manifest, archive digest, and entry table verify. Restores verify each archive member's path, size, and SHA-256 against the backup manifest before applying any file. Each applied or preserved entry is journaled, so an interrupted restore can safely be repeated; conflicting existing files remain unless the caller explicitly requests overwrite. Restoring the installer database is a separate explicit option, validates its schema and integrity, takes a pre-restore snapshot, and uses the installer lock.

Every operation records a checkpoint and append-only redacted event. A failed stage includes its stage name, exit code or safe error type, a bounded diagnostic path, observed effect snapshot, and `hermes-installer resume` instruction. Diagnostic output is capped and scrubbed before persistence. A partial Desktop renderer directory does not count as a native product; the packaged Linux ARM64 application must be present before the product stage is accepted.

Bootstrap requests the pinned installer script through the fixed `artifact.fetch` verb, bound to its enrolled artifact ID, SHA-256 digest, and byte limit. The broker returns an opaque store receipt; the bootstrap process passes only that ID, and the root custodian resolves it from the immutable protected catalog before launch. Script bytes and protected catalog paths never enter the profile-owned cache or process request. Process start, status, output reads, and stop use `process.start`, `process.status`, `process.read`, and `process.stop`; each operation gets a fresh host-issued grant and a canonical request digest. Output and diagnostics stay bounded, receipts enter the private journal, and cancellation/error cleanup is reported only after the host verifies it.

The root-owned handlers and protected profile registry still need to be enrolled before these effects can run on a target. In particular, the upstream installer stage also fetches source and dependencies; the worker network remains denied until those inputs are pre-staged through reviewed artifact/package effects. Bootstrap must not substitute direct child/process-group signaling or direct network fetches. Until the fixed handlers, script-path pin, and source/dependency broker path are enrolled, those stages remain unavailable with a resume instruction. This prerequisite state is not evidence of a completed install.

`hermes-installer update check` verifies the active immutable generation without creating state. Update apply and rollback remain pending until the pinned candidate, protected host launch handler, and actual Hermes health probe are enrolled; they do not switch generations in that state. `hermes-installer data backup` creates a versioned backup, `--include-database` opts into the installer SQLite snapshot, and `data restore --backup <path>` restores only from the managed backup store while preserving conflicts. `--overwrite` replaces conflicts explicitly and `--restore-database` separately opts into the versioned database restore. `data uninstall` refuses while the journal reports an active service or the verified active-generation pointer remains set; it removes only inactive verified owned generations while retaining profiles, overlays, memories, models, and backups. Active process shutdown/deactivation still requires host custody. These commands use the same exclusive installer lock and expose structured results.

`hermes-installer setup` runs the account/component wizard under the exclusive lifecycle lease, records only non-secret selections and account states, and can write its validated secret-reference-only result to a new mode-0600 file with `--save-config`. Interactive mode requires a terminal; `--non-interactive` accepts only explicit secure references and performs no prompts. `install` and `resume` use durable configuration selection and stage checkpoints, but product stages remain unavailable when the root-owned artifact/process handlers or source and dependency broker inputs are missing. Provider-account provisioning and native runtime acceptance remain separate work. Physical Pi, account, and native runtime evidence are not inferred from temporary fixture tests.
