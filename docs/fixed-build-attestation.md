# Fixed source-build execution and output attestations

The root authority build layer accepts only the protected `process.start` selection envelope: `enrollment_id`, `generation`, one of the fixed Sol operation IDs, and `parameters: {}`. The IDs map to `coral-cpython-build:start` and `colibri-source-build:start`. The worker cannot choose an executable, source/toolchain artifact, compiler flag, path, output name, or environment value.

`RootBuildExecutionService` resolves the protected build profile and the exact source, toolchain, and builder pins through the root `ArtifactCatalog`. It passes those resolved records, the fixed argv recipe, and the enrolled output root to a root-only managed build-job launcher. The service accepts success only from a terminal receipt with the selected generation, expected builder UID, exit code zero, verified cleanup, and exact private-network, address-deny, no-new-privileges, and protected-filesystem readbacks. A live PID or a start receipt is not build completion.

Every declared output must have a root-enrolled finite output constraint (relative path, maximum size, executable role, and target ABI facts). The root observes its actual size and SHA-256 only after the managed job has exited successfully; pre-enrolling a compiled-output digest would be circular. The service scans the complete output tree without following symlinks, rejects extra/missing files, verifies owner, mode, bounds, digest and enrolled target facts, then copies actual bytes into a root-owned content-addressed store. It fsyncs and atomically publishes the signed attestation and the current target/generation index only after all outputs verify. If authorization expires or any check fails, the current receipt is not advanced; unreferenced CAS objects may remain for safe garbage collection. The present protected profile still uses static `required_outputs` hashes; the dynamic constraint schema requires a Sol-owned append-only refinement before this service can be composed.

Attestations are HMAC-signed with a build-specific key derived from the 32-byte root authority key. Each record binds the selected operation, enrollment and generation, source/toolchain/builder pins, canonical recipe digest, complete observed output manifest, and terminal process identity/limits. The issued receipt digest is dynamic and must not be pre-pinned into package enrollment; enrollment pins recipe constraints and resolves the signed receipt after execution. `resolve(profile)` rechecks the signature and all current profile pins. `resolve_output(profile, artifact_id)` returns a path only when that opaque output ID is in the current verified receipt and the root-owned CAS bytes still match.

The handler remains deliberately unregistered: the current managed-process boundary provides selection-only start receipts but no authoritative one-shot build completion API. `HW-T03` stays incomplete until a root-owned launcher supplies the typed terminal result and enrollment supplies explicit output specifications. No native ARM64 build, CPython ABI qualification, Colibri runtime qualification, or target acceptance is claimed here. GLM-5.2 model files are not build outputs and are never downloaded by this path.
