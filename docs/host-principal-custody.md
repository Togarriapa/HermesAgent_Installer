# Host principal custody implementation status

This document records implementation evidence separately from Linux runner, native ARM64, and Pi acceptance. The current branch contains an authority-broker client and a root-side fixed process handler. Neither local source nor fixture results establish that a protected daemon is installed or that a native Hermes worker has passed target qualification.

## Process admission contract

`hermes_installer.managed_process.ManagedProcessSpec` binds a resolved executable and SHA-256 pin, opaque child-artifact references resolved only by the root catalog, one profile data root, a minimal environment allowlist, a dedicated service UID, a finite startup deadline, manager-enforced lifetime/output bounds, and optional cgroup limits. A host-issued `HostContext` and one-use `EffectAuthorization` are required; the context and grant bind the complete canonical launch envelope. Protected profile enrollment supplies an exact argv recipe: interpreters may run only one enrolled immutable child artifact, while other executables must match root-enrolled literal arguments exactly. Caller `-c`/inline interpreter code, script paths, and extra app flags cannot broaden the recipe. Secrets in argv or environment are rejected. The service UID is `hermes-` plus the first 16 hex characters of SHA-256(profile ID), with no login shell, home directory, or supplemental groups. The profile root is mounted at `/hermes/profiles/<profile_id>` while `HERMES_HOME=/hermes`, preserving Hermes' native `profiles/<name>` lookup without exposing sibling profile data.

`ManagedProcessEffectHandler` is the root-only adapter for fixed `process.start/status/read/write/stop` verbs with operation-specific control targets. It accepts only the already-verified consumed grant, checks protected profile/catalog bindings, duplicates the pidfd captured from SO_PEERCRED at connection acceptance, starts an exact systemd transient unit, reads kernel UID/cgroup/namespace/executable and cgroup limit evidence, and owns cgroup stop/escalation. Before `systemd-run`, it bounds manager-environment preparation by the remaining grant lifetime and rechecks the current registration, peer pidfd, deadline and cancellation state; prepared artifact mount slots are removed on denial. `ManagedProcessSupervisor.start(spec)` talks only through `AuthorityClient.process_start`; its handle uses fixed broker controls and bounded separate stream cursors. It never signals a caller-supplied PID or process group. `run_managed_process` captures bounded stdout and stderr separately and records cleanup proof.

## Root-selected process control

`authority.process_controls.process_control_operation` is the worker-side API for controlling a started process. It accepts only a fixed `process.status`, `process.read`, `process.write`, or `process.stop` verb, the opaque `process_id`, its generation, and bounded verb-specific fields. The fixed `process.control` AF_UNIX request contains no profile, target, data root, capability, context or portable grant. Root authenticates the socket peer, resolves the live handle and generation through the custodian registry, derives the selected profile operation target, and issues and consumes a current one-use grant for that exact canonical payload. Unknown handles, foreign peers, stale generations, replay, cancellation, deadline expiry and custodian identity changes fail closed.

`read` selects stdout/stderr and at most 1 MiB; the root maintains stream cursors. `write` selects the next one-use frame sequence and up to 256 KiB of bytes, encoded as canonical base64 only for the JSON AF_UNIX wire. `stop` accepts only a fixed lifecycle reason (`cancel`, `shutdown`, or `rollback`) and a grace period from zero to ten seconds. `inspect` is also a fixed control verb and returns only the root's HI10 attestation. Every response binds schema, process handle, generation, operation, state, typed result and expiry. Stop success requires the custodian's cleanup proof; a response without completed reaping remains a failure. This source contract and fixture evidence do not establish a deployed daemon, Linux kernel effects, or Pi/native acceptance.

## Current limits

The daemon constructor and handler factory exist in source, but the root-owned daemon, protected profile/catalog registry, socket directory, and per-UID sockets have not been installed or exercised on Linux. Child scripts must be staged in an immutable root-owned catalog and explicitly enrolled by opaque ID and digest; caller-owned bootstrap staging is rejected. A dedicated Ubuntu 24.04 root integration workflow now constructs a disposable `AuthorityService`, profile UID, protected fixture catalog and actual transient systemd units. It probes host-file/credential/procfs/signal/network denials, parent-death and stubborn-descendant cgroup cleanup, plus signed but unenrolled interpreter argv, slow-preparation expiry, and prelaunch cancellation. This suite has only passed static syntax/whitespace review so far; CI execution is still required. Network namespaces deny worker egress; the HI07 fixed local-service connector and reviewed broker-only download/egress route remain unimplemented, so network-backed stages stay unavailable.

The host authority fixtures are synthetic contract fixtures. They do not prove production Authentik, actual authority key custody, or target policy enrollment. Linux integration coverage is in `tests/contracts/test_managed_process_custody_linux.py`; its controlled policy and test-only catalog are explicitly not production authority evidence, and the workflow has not yet run. Native ARM64 and Pi start/stop/parent-death, sibling filesystem/process/network/credential denials remain pending. No task is marked as native acceptance.

## Root-observed native loader custody (HI08 / HI09)

`authority.native_custody_proof.RootNativeLoaderObservationStore` joins three separate facts before it returns `LoadedPackageClosureProof`: a current manager-owned process/PIDFD, the custody manager's revalidated immutable mount receipt, and the selected loader's completed private progress channel. It creates a launch-private `0700` directory and `0600` AF_UNIX listener, then supplies only its fixed socket path as systemd v253+'s `OpenFile=<path>:hermes-loader-progress` unit property. It does not expose the path or nonce in worker argv/environment and does not use a path proxy; root accepts the manager connection directly and challenges the loader with a root-generated nonce. The receiver accepts only the canonical length-prefixed JSON sequence `entrypoint-imported`, `actions-registered`, `ready`, checks per-segment Linux `SCM_CREDENTIALS` against the live child PID/UID/GID and root PIDFD custody, rejects ancillary descriptors and closes the observation on cancellation, replay, changed identity, mismatched mount/action digests, unexpected EOF or any fourth frame. `SO_PEERCRED` on the manager's connection is not child proof. Mount metadata by itself never enters the ready registry.

The stable proof is cached per launch and source-observer enrollment; each lookup still rechecks the kernel peer, generation and mount, and its original lease is never renewed. `active_native_catalog_resolver` derives the package, main entrypoint role, finite action set and adapter-role/action joins from `RootRuntimeBindings` plus typed active observer enrollments. `attach_root_source_observers` supplies this proof adapter and the same root store's invocation-specific target PIDFD resolver to `SourceObserverRegistry`. `native_bridge_source_target_selector` uses `NativeBridgeBroker.resolve_pending_pair_for_context` and the pair's explicit `observer_delivery_bindings` to select producer or gateway; target/recipient strings and caller PID/profile selectors are never used to choose a peer. The pinned loader's selected package hook retrieves only systemd's fixed named `hermes-loader-progress` descriptor, receives the root-generated nonce challenge, and emits progress after the selected entrypoint imports and each adapter registers its reviewed actions. This proves readiness of that selected action table; it does not prove an action succeeded or establish user provenance. `ManagedProcessEffectHandler` enforces systemd v253+, creates and passes the named `OpenFile` endpoint for native-package launches, retains the actual handle, and blocks success until the root receiver validates the ready sequence. A Linux root transient-unit regression is wired into the host-custody workflow, but the previous run was on a pre-cleanup commit and does not verify the cleanup fix. Runtime composition now attaches and closes the store/registry conditionally, but the daemon's current active service builder does not construct the protected `NativeBridgeBroker` or supply complete explicit observer-delivery role bindings, so this composition remains unavailable there. Actual Linux credential transport, an active root composition, native ARM64 and Pi evidence remain open under HI-T08/HI-T09.

Native bridge rows carry explicit producer/gateway observer-delivery maps; a peer role artifact is resolved only from that peer's unique current protected package closure. The native MCP dispatch rows remain digest-covered and resolve only when current process custody, package adapter, selected MCP tool/resource scope, and the exact effect rule agree. HI13 gateway boundary selection can use a current root custody proof; native-window selection remains unavailable until the selected Xauthority startup receipt can be resolved and inode-checked. Catalog rows alone do not assert current runtime readiness.

## Fixed local service connector (HI07)

`hermes_installer.service_connector` adds a protected connector for the exact enrolled `xpra-native` and `colibri-main` service targets. Its worker-facing API returns an opaque typed stream handle (`connector_id`, generation, expiry, frame limit and byte budget) and exposes only sequenced `read`, `write` and `close` operations. Root resolves a protected live service handle and namespace; caller data cannot select a PID, URL, host, port, route outside the fixed catalog or namespace. Each verb requires a fresh one-use grant bound to the same target, route, session, peer PIDFD, source lineage and bounded lease. The root watchdog retains bidirectional close authority and reaps expired or cancelled streams. See [fixed-service-connector.md](fixed-service-connector.md) for the API and current fixture boundary.

The route catalog currently contains Xpra HTTP/WebSocket at namespace-local loopback port 14500 and Colibri's OpenAI-compatible inference API at namespace-local loopback port 8000. The connector has a loopback fixture effect/denial suite wired into the root Ubuntu Linux workflow. Local source and macOS skipped tests do not establish Linux namespace effects; the authority operation rules/daemon registration, protocol-specific allowlist enforcement, successful Linux CI result, native desktop and Pi service evidence remain pending. Memory/MCP routes are not enrolled by this connector.

## Root-observed remote connector authority (HI13)

`authority.remote_connector_authority.RemoteConnectorEffectAuthority` is the root-only dual-principal issuer and one-use consumer for HI13 connector effects. It preserves the currently registered gateway PIDFD identity as the controlling process, while deriving the effective principal from the verified Access session and the effective profile/generation, target and route from the protected native enrollment. Issuance and consumption both re-read current enrollment, policy/config revision, service generation, boot epoch, gateway process identity, immutable gateway role and entrypoint proof, and HI13 session state. The exact canonical HI07 payload digest, sequence and original session deadline are bound into the authorization. The consumer removes its nonce before asking HI12 to atomically spend the underlying connector capability; replay, cross-profile substitution, stale identity/configuration, revocation and expiry deny before the socket adapter can send bytes.

`AuthorityServiceHI12Adapter` resolves exactly one active service UID for the enrolled native profile/generation. It creates the effect context inside the root `AuthorityService`, obtains the fixed operation/target grant through its policy and enrollment checks, and validates the signed context/grant again at consumption before the service's atomic nonce spend. The active protected service-generation digest and host boot epoch must still match. It never accepts a worker-supplied HostContext or profile selector.

The component exposes `issue_remote_connector_effect(binding, operation, canonical_payload, ...)` and `consume_remote_connector_effect(authorization, binding, operation, canonical_payload, sequence, ...)` for root assembly. Its injected registry, PIDFD inspector, role/entrypoint proof, HI13 session check and HI12 issuer/consumer must all be protected root adapters. Contract fixtures cover successful exact issuance/spend, replay, sibling-profile and payload mismatch, PID replacement, stale policy/native generation and revocation. These fixtures do not establish the production registry, separate Linux principal effects, namespace socket result or actual Cloudflare/native Desktop acceptance; those remain open under HI-T13/RT-F03.

## First-setup Authentik principal receipts (HI-T03 / BD-F01)

`authority.setup_principal.RootSetupIdentityIntake` is the stage-zero root-local intake. It accepts only the installed `RootInitialCompilationRegistry` and the exact `InstalledRootSetupActorVerifier` attached to it. The current root actor plan and immutable installed Authentik policy template are reverified before selection or credential intake. The user may select an HTTPS origin and exact System/recipient group IDs; the policy revision is read from the pinned template. A credential can come from an existing root-vault reference or a hidden root setup terminal prompt. Raw credential text is never accepted as a method argument, argv/environment value, worker request, or user-private journal value. User-mode credential references are not accepted as root-vault evidence.

After first publication, `RootSetupSessionStore.begin_from_initial_publication(handoff_handle)` resolves the typed factory handoff, verifies the stage-zero session and selected plan, creates a new root-local setup transaction from the sealed choices, durably records a pending adoption, and consumes the handoff once into the normal session. The principal registry then requires a fresh authenticated-identity receipt for that normal session and checks it against the original Authentik subject and root-vault reference before minting a new principal-selection handle. It never carries a stage-zero observation lease into active setup. `verify_committed_receipt(receipt, authorization)` joins the returned pathless receipt to exactly one root-owned transaction journal, the current selected generation digest, the setup transaction/plan/target, and its compare-and-swap predecessor; `consume_selected_principal` accepts only that store-issued verification result.

`RootSetupAuthentikIdentityObserver` accepts either a live root setup-session handle or the exact stage-zero compilation registry/session handle. Its policy resolver is the `RootSetupIdentityIntake` instance, which resolves a handle only against the current session/transaction/plan, installed template and root journal. The observer resolves the selected secret from `RootCredentialVault` with the `authentik-system-read` scope, then reuses Authentik's TLS/no-redirect transport, current-user uniqueness/active-subject checks and bounded cycle-safe complete group walk at only `/api/v3/core/users/me/` and the root-observed group paths. It stores a random short-lived receipt (at most 30 seconds and no longer than the current setup session) under the selected root journal. The receipt stores the credential reference and identity/group observation, never token bytes.

`RootSetupPrincipalSelectionRegistry.from_initial_compilation(...)` accepts that opaque identity receipt before the first policy or active worker exists. The same registry also supports `from_root_setup(...)` for later normal sessions. It re-observes the current subject and complete group hierarchy, binds the receipt to the current setup session/transaction/plan, derives a stable principal ID from the Authentik subject, and asks the root-reviewed capability selector for the fixed profile, namespace and capability tuple. `resolve_selected_principal(handle, session, transaction, plan_digest)` repeats the session, identity, expiry and capability checks before compilation. The selected identity is not the root operator. The service `PrincipalBinding` joins the actual dedicated NSS service UID only at activation; after the matching committed enrollment CAS, `consume_selected_principal(..., activation_receipt)` writes a one-use consumption record. System-group absence is preserved as an observed identity fact and is not an authorization to perform protected writes.

After the published handoff is adopted, `resolve_adopted_initial_principal(store, session)` locates the unique root-journaled adoption record for that live normal session and performs the same current Authentik and capability revalidation before returning its typed selection. Stage-zero receipt handles are not required in a wizard journal. `RootAuthorityKeySelectionRegistry` similarly binds only a concrete stage-zero session from the installed release registry; it preserves an existing `/etc/hermes-installer/authority.key`, creates one only with an exclusive first-install journal, and writes a separate root-owned `authority-key-<random-id>` selection receipt containing key device/inode but no key bytes or digest. Ambiguous interruption or foreign custody is left for root reconciliation rather than silently adopting or rotating a key.

The contract suite includes a local HTTPS Authentik fixture and rejects unsafe origins/group choices, untyped stage-zero registries and group cycles, as well as stale/revoked subjects, expired or cross-session handles, symlinked receipts and receipt replay. Its root/vault/NSS account transaction is Linux-only and skipped on the development macOS host. Fixture success does not establish a production Authentik account, installed setup UI/root-vault intake, active service, or Pi acceptance; those remain separate gates.
