# Host principal custody implementation status

This document records implementation evidence separately from Linux runner, native ARM64, and Pi acceptance. The current branch contains an authority-broker client and a root-side fixed process handler. Neither local source nor fixture results establish that a protected daemon is installed or that a native Hermes worker has passed target qualification.

## Process admission contract

`hermes_installer.managed_process.ManagedProcessSpec` binds a resolved executable and SHA-256 pin, opaque child-artifact references resolved only by the root catalog, one profile data root, a minimal environment allowlist, a dedicated service UID, a finite startup deadline, manager-enforced lifetime/output bounds, and optional cgroup limits. A host-issued `HostContext` and one-use `EffectAuthorization` are required; the context and grant bind the complete canonical launch envelope. Protected profile enrollment supplies an exact argv recipe: interpreters may run only one enrolled immutable child artifact, while other executables must match root-enrolled literal arguments exactly. Caller `-c`/inline interpreter code, script paths, and extra app flags cannot broaden the recipe. Secrets in argv or environment are rejected. The service UID is `hermes-` plus the first 16 hex characters of SHA-256(profile ID), with no login shell, home directory, or supplemental groups. The profile root is mounted at `/hermes/profiles/<profile_id>` while `HERMES_HOME=/hermes`, preserving Hermes' native `profiles/<name>` lookup without exposing sibling profile data.

`ManagedProcessEffectHandler` is the root-only adapter for fixed `process.start/status/read/write/stop` verbs with operation-specific control targets. It accepts only the already-verified consumed grant, checks protected profile/catalog bindings, duplicates the pidfd captured from SO_PEERCRED at connection acceptance, starts an exact systemd transient unit, reads kernel UID/cgroup/namespace/executable and cgroup limit evidence, and owns cgroup stop/escalation. Before `systemd-run`, it bounds manager-environment preparation by the remaining grant lifetime and rechecks the current registration, peer pidfd, deadline and cancellation state; prepared artifact mount slots are removed on denial. `ManagedProcessSupervisor.start(spec)` talks only through `AuthorityClient.process_start`; its handle uses fixed broker controls and bounded separate stream cursors. It never signals a caller-supplied PID or process group. `run_managed_process` captures bounded stdout and stderr separately and records cleanup proof.

## Root-selected process control

`authority.process_controls.process_control_operation` is the worker-side API for controlling a started process. It accepts only a fixed `process.status`, `process.read`, `process.write`, or `process.stop` verb, the opaque `process_id`, its generation, and bounded verb-specific fields. The fixed `process.control` AF_UNIX request contains no profile, target, data root, capability, context or portable grant. Root authenticates the socket peer, resolves the live handle and generation through the custodian registry, derives the selected profile operation target, and issues and consumes a current one-use grant for that exact canonical payload. Unknown handles, foreign peers, stale generations, replay, cancellation, deadline expiry and custodian identity changes fail closed.

`read` selects stdout/stderr and at most 1 MiB; the root maintains stream cursors. `write` selects the next one-use frame sequence and up to 256 KiB of bytes, encoded as canonical base64 only for the JSON AF_UNIX wire. `stop` accepts only a fixed lifecycle reason (`cancel`, `shutdown`, or `rollback`) and a grace period from zero to ten seconds. `inspect` is also a fixed control verb and returns only the root's HI10 attestation. Every response binds schema, process handle, generation, operation, state, typed result and expiry. Stop success requires the custodian's cleanup proof; a response without completed reaping remains a failure. This source contract and fixture evidence do not establish a deployed daemon, Linux kernel effects, or Pi/native acceptance.

## Current limits

The daemon constructor and handler factory exist in source, but the root-owned daemon, protected profile/catalog registry, socket directory, and per-UID sockets have not been installed or exercised on Linux. Child scripts must be staged in an immutable root-owned catalog and explicitly enrolled by opaque ID and digest; caller-owned bootstrap staging is rejected. A dedicated Ubuntu 24.04 root integration workflow now constructs a disposable `AuthorityService`, profile UID, protected fixture catalog and actual transient systemd units. It probes host-file/credential/procfs/signal/network denials, parent-death and stubborn-descendant cgroup cleanup, plus signed but unenrolled interpreter argv, slow-preparation expiry, and prelaunch cancellation. This suite has only passed static syntax/whitespace review so far; CI execution is still required. Network namespaces deny worker egress; the HI07 fixed local-service connector and reviewed broker-only download/egress route remain unimplemented, so network-backed stages stay unavailable.

The host authority fixtures are synthetic contract fixtures. They do not prove production Authentik, actual authority key custody, or target policy enrollment. Linux integration coverage is in `tests/contracts/test_managed_process_custody_linux.py`; its controlled policy and test-only catalog are explicitly not production authority evidence, and the workflow has not yet run. Native ARM64 and Pi start/stop/parent-death, sibling filesystem/process/network/credential denials remain pending. No task is marked as native acceptance.

## Protected enrollment and distinct roots (HI09)

`hermes_installer.protected_enrollment` defines the root-owned catalog boundary. Its signed canonical manifest maps only `(enrollment_id, generation)` to an immutable profile, owner UID/GID/name, executable and digest, runtime artifact IDs, policy IDs, and distinct home/work/data roots. The resolver rejects unknown or stale generations, non-distinct roots, incorrect service ownership/mode, writable or symlinked ancestors, and caller-provided physical identifiers. `resolve_operation` returns a target only for a root-enrolled fixed operation; `resolve_connector_route` maps a logical target/route to the enrolled profile and namespace identity. Both return policy metadata, not a descriptor or independent namespace authority. The root custodian must still retain and revalidate the process/namespace handles for each connector lease.

The root authority loader now consumes one strict, root-owned `service_generations` snapshot whose canonical digest covers service profiles, devices, builds, native packages, memory routes, operation schemas, source issuers, resource jobs, and remote sessions. It joins six exact process targets and their authority rules to the selected service UID/GID, principal, namespace, and generation. The daemon constructs the process manager, artifact/package handlers, and fixed connector handlers once from that verified enrollment. `process.start` takes only enrollment ID, generation, fixed recipe ID, and typed scalar parameters; the manager resolves executable, argv, cwd, environment, and the distinct home/work/data roots from the root catalog. Optional absent package-set enrollment leaves `package.install` unavailable; malformed present enrollment still denies startup.

Native package mounting now resolves the unique package for the root-selected profile generation, materializes only protected catalog artifacts, and asks custody to verify the complete immutable closure before the read-only namespace mount. Source-issuer metadata is parsed from the active generation digest, but source receipt issuance remains unavailable until a loaded-package proof and authenticated target-role delivery channel exist. Coral device access remains unavailable without selected device-cgroup enforcement; source-build/runtime activation remains unavailable without a qualified root build runner and current dynamic output attestation. These source integrations and fixtures do not establish an installed root daemon, dedicated service-account/root provisioning on a target, native ARM64 execution, actual namespace/kernel enforcement, or Pi acceptance.

## Fixed local service connector (HI07)

`hermes_installer.service_connector` adds a protected connector for the exact enrolled `xpra-native` and `colibri-main` service targets. Its worker-facing API returns an opaque typed stream handle (`connector_id`, generation, expiry, frame limit and byte budget) and exposes only sequenced `read`, `write` and `close` operations. Root resolves a protected live service handle and namespace; caller data cannot select a PID, URL, host, port, route outside the fixed catalog or namespace. Each verb requires a fresh one-use grant bound to the same target, route, session, peer PIDFD, source lineage and bounded lease. The root watchdog retains bidirectional close authority and reaps expired or cancelled streams. See [fixed-service-connector.md](fixed-service-connector.md) for the API and current fixture boundary.

The route catalog currently contains Xpra HTTP/WebSocket at namespace-local loopback port 14500 and Colibri's OpenAI-compatible inference API at namespace-local loopback port 8000. The connector has a loopback fixture effect/denial suite wired into the root Ubuntu Linux workflow. Local source and macOS skipped tests do not establish Linux namespace effects; the authority operation rules/daemon registration, protocol-specific allowlist enforcement, successful Linux CI result, native desktop and Pi service evidence remain pending. Memory/MCP routes are not enrolled by this connector.

## Root-observed remote connector authority (HI13)

`authority.remote_connector_authority.RemoteConnectorEffectAuthority` is the root-only dual-principal issuer and one-use consumer for HI13 connector effects. It preserves the currently registered gateway PIDFD identity as the controlling process, while deriving the effective principal from the verified Access session and the effective profile/generation, target and route from the protected native enrollment. Issuance and consumption both re-read current enrollment, policy/config revision, service generation, boot epoch, gateway process identity, immutable gateway role and entrypoint proof, and HI13 session state. The exact canonical HI07 payload digest, sequence and original session deadline are bound into the authorization. The consumer removes its nonce before asking HI12 to atomically spend the underlying connector capability; replay, cross-profile substitution, stale identity/configuration, revocation and expiry deny before the socket adapter can send bytes.

The component exposes `issue_remote_connector_effect(binding, operation, canonical_payload, ...)` and `consume_remote_connector_effect(authorization, binding, operation, canonical_payload, sequence, ...)` for root assembly. Its injected registry, PIDFD inspector, role/entrypoint proof, HI13 session check and HI12 issuer/consumer must all be protected root adapters. Contract fixtures cover successful exact issuance/spend, replay, sibling-profile and payload mismatch, PID replacement, stale policy/native generation and revocation. These fixtures do not establish the production registry, separate Linux principal effects, namespace socket result or actual Cloudflare/native Desktop acceptance; those remain open under HI-T13/RT-F03.
