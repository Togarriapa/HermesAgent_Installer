# Memory provider integration

Memory records are owned by one capture provider per profile. Hermes continues to own conversation coordination; the installer injects the guarded per-profile HERMES_HOME and separately supervises each provider's service/data directory. Changing owner flushes and stops the former capture stream before selecting the new one. A failed transition is journaled; if compensating service effects cannot be confirmed, the prepared entry remains and blocks reads or another owner change until supervised host recovery. Retrieval may select a compatible provider, but never makes it a second automatic capture owner.

The adapters in `src/hermes_installer/memory/providers.py` address only opaque host broker targets. They contain no HTTP transport, endpoint, credential-file lookup, or process launcher. The root-owned broker enrolls fixed target IDs and translates each provider operation to the pinned native API. Agent Memory targets its selected rohitg00/agentmemory source; its upstream export endpoint is not namespace-scoped, so the broker must bind it to the profile's isolated service/data root before enabling export or delete. OpenViking and claude-mem workers must already be running under host custody before `doctor` can succeed. Their native setup paths never run from a Hermes hook.

Capture receives a signed source HostContext. Extraction and embedding are separate effects, each with a new host-issued context derived from the source lineage and each requiring their own protected target and capability. The adapter persists facts only after both effects succeed. A missing broker, grant, service handler, embedding route, or valid response fails closed before persistence. Provider retries and queued hooks must acquire fresh contexts and grants for each attempt; caller labels and saved grants are not authority.

A broker-fixture contract verifies payload digests, fixed target IDs, distinct extraction/embedding/capture grants, namespace filtering, and recursion rejection. Fixture success is not service, sandbox, account, native hook, or hardware acceptance. Live acceptance remains pending until a root-owned broker with peer-credential checks and protected handlers is installed, all private operations are routed through it, supervised provider services pass the pinned native API checks, and synthetic data survives a real service restart and fresh Hermes session. Backup returns an opaque service archive with an integrity digest and signed source lineage. Restore is a distinct fixed broker effect; it cannot be expressed as ordinary capture, and the broker must verify that the archive's profile/namespace match the host context. Deletion and disablement use the same profile-owned journal and broker scope. These operations have contract fixtures only until their protected handlers and isolated service custody are enrolled.


## Exact upstream route contracts

The provider revisions are pinned in `src/hermes_installer/memory/broker.py`. The route and payload mappings were checked against the corresponding primary source files:

- [OpenViking sessions API at the pinned revision](https://github.com/volcengine/OpenViking/blob/e7b2e974b1fb97cd8c6087ff013181ddfec94f77/docs/en/api/05-sessions.md) and [retrieval API](https://github.com/volcengine/OpenViking/blob/e7b2e974b1fb97cd8c6087ff013181ddfec94f77/docs/en/api/06-retrieval.md). Retrieval uses `POST /api/v1/search/find` scoped to `viking://~/memories` and memory context only. Capture is a broker-side fixed sequence over create-session, add-message, and commit; the generic connector must implement this fixed sequence and must not accept caller URLs. The separate service must be prestarted with lazy installs disabled and a sanitized environment.
- [Claude-mem API at the pinned revision](https://github.com/thedotmack/claude-mem/blob/fa8ab09f06aa05f958c5225cf3756ce52a3ebb96/docs/api.md) and [memory route schemas](https://github.com/thedotmack/claude-mem/blob/fa8ab09f06aa05f958c5225cf3756ce52a3ebb96/src/core/schemas/memory-item.ts). The REST API exposes `GET /healthz`, `POST /v1/search`, `POST /v1/memories`, and `DELETE /v1/memories/:id`. Writes require `projectId`, `kind`, and `type`; search is scoped with the enrolled project ID.
- [AgentMemory REST routes at the pinned revision](https://github.com/rohitg00/agentmemory/blob/df3d4a83b966d8d415cb9180d5a4724b07f729dc/src/triggers/api.ts). Liveness is `GET /agentmemory/livez`; capture, search, deletion, export, and import are `POST /agentmemory/remember`, `POST /agentmemory/smart-search`, `POST /agentmemory/forget`, `GET /agentmemory/export`, and `POST /agentmemory/import`. The service's export is global to that instance, so the protected catalog must allocate a separate service and data root for every profile. Capture currently has no native arbitrary provenance-metadata field; the broker stores opaque record, source, and lineage identifiers in supported concepts fields, while the root queue/journal remains the authoritative private lineage record.

The broker caps inbound request bytes at 256 KiB, provider responses at 1 MiB, each fact at 8 KiB, facts per operation at 64, and timeouts at 30 seconds (normally 20 seconds or less). Oversized provider output is rejected; the connector must enforce the same response cap before buffering. AgentMemory's upstream export may exceed this cap for large profiles; such a backup/export remains unavailable until a bounded pagination or streaming archive path is verified. No source API pin by itself proves that a provider can safely run inside the current process-custody model.


## Durable capture consent and owner changes

Each asynchronous capture row is paired with the exact root-signed background-consent wire object and a durable consent ID bound to profile, provider, and the integer owner-ledger epoch. The root authority's active-consent callback reads the protected journal and current owner epoch; an unreadable or prepared transition denies background effects. Each worker stage asks the root service for fresh context/effect authorization from the original signed source provenance. It never reuses the enqueue grant as stage authority.

Changing the durable owner epoch makes prior consents inactive immediately. After the owner transition commits, cleanup marks the matching consent rows inactive and erases queued or in-flight journal payload bytes. If cleanup is unavailable, the epoch mismatch still prevents processing and the runtime reports the cleanup failure. The queue exposes a single-job worker object for a supervised host worker, but does not start a thread or process until custody provides an authenticated service/worker contract. Thus these changes establish durable queue and consent behavior; they do not claim live provider execution or restart retrieval.

### Broker route enrollment

Memory effects cross the service boundary using protected opaque route IDs. The root broker verifies the signed host context and consumed effect authorization before any connector bytes, then selects an ID from the provider/action table and checks that ID against `approved_route_ids` in the protected per-profile enrollment. No plugin or worker supplies a method, path, URL, host, or port. The connector receives the context and grant, service identity/generation, opaque route ID, signed trace ID, bounded monotonic deadline, and payload. When custody provides the fixed connector import and service-generation API, this contract can be connected; until then runtime `ipc` stays unavailable and no provider request is sent.
