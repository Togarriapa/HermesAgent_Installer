# Registry runtime

The importer treats HermesAgent_Resources as a versioned declarative catalog. It resolves only explicit selectors and dependency/inheritance edges, rejects missing nodes and cycles, and merges nested maps while lists use child replacement. A declaration is not a host grant: every capability also requires a host grant and current runtime authorization.

The eight nonrecursive roots are profiles, skills, plugins, MCPs, bundles, channels, crons and webhooks. `hermes-installer resources plan` and `hermes-installer resources status` validate the packaged source offline and report its per-item crosswalk. Materialization generates Hermes `SKILL.md` files under the owned default home and isolated Hermes profile homes with separate `SOUL.md`, `config.yaml`, and `profile.yaml` files. Profile homes are launched only through the internal orchestrator; putting a profile in a prompt does not enforce that boundary.

The immutable generation also carries `installer-registry/crosswalk.json`. Each entry binds the source path, version, and revision to its installed path and adapter identity, and records bundled, validated, materialized, discovered, authenticated, functional, enabled, and target-verified states separately. `registry.resources_runtime` supplies typed Hermes plugin registration, profile-pinned local overlays, internal bundle rosters, cron/channel/webhook effect envelopes, and authenticated/replay-protected webhook verification. Every network, account, process or scheduled effect requires fresh root-issued context, exact resource target, one-use authorization and a fixed host operation. Resource declarations never provide endpoints or grants.

Runtime records are generated disabled. Plugin discovery is emitted only when a reviewed `register(ctx)` handler is available. MCPs require an enrolled fixed server target and account. Bundle rosters resolve against the pinned closure; the root Hermes topology is kept separate from internal recruitment. Cron profile-run, Hermes-only channel route and verified webhook delivery use `resource.cron.run`, `resource.channel.route` and `resource.webhook.deliver` fixed verbs. Those root handlers and protected targets remain unavailable until separately enrolled and verified; the staged declaration alone is not functional, enabled or target-verified. Webhook receipts never authorize effects. Profile overlay values are private, revisioned and compare-and-swap protected; encryption, backup and restore remain separate capabilities.

The contract test `tests/contracts/test_registry_resources_runtime.py` exercises authorization ordering and digest binding, target-spoof denial, native registration unavailability, fixed Hermes routing, webhook signature/replay rejection, manifest policy guards and private overlay CAS/tombstones. Execute it in Linux CI with the project runtime suite; it is not Pi or account acceptance evidence.

Each generated generation is immutable. Stage into a new owned directory, validate files and policy, then atomically replace the active pointer. Failures retain the previous pointer and user data. Authorization must be checked at the actual tool/process/filesystem boundary, including fresh identity lookup for homelab writes; profiles and prompts are not a sandbox.

Hermes alone faces the user. It routes correlated work to bounded internal specialists and receives evidence and dissent before composing a response. Specialists have separate state and cannot bind user channels.
