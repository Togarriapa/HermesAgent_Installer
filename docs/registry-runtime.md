# Registry runtime

The importer treats HermesAgent_Resources as a versioned declarative catalog. It resolves only explicit selectors and dependency/inheritance edges, rejects missing nodes and cycles, and merges nested maps while lists use child replacement. A declaration is not a host grant: every capability also requires a host grant and current runtime authorization.

The eight nonrecursive roots are profiles, skills, plugins, MCPs, bundles, channels, crons and webhooks. `hermes-installer resources plan` and `hermes-installer resources status` validate the packaged source offline and report its per-item crosswalk. Materialization generates Hermes `SKILL.md` files under the owned default home and isolated Hermes profile homes with separate `SOUL.md`, `config.yaml`, and `profile.yaml` files. Profile homes are launched only through the internal orchestrator; putting a profile in a prompt does not enforce that boundary.

The immutable generation also carries `installer-registry/crosswalk.json`. Each entry binds the source path, version, and revision to its installed path and adapter identity, and records bundled, validated, materialized, discovered, authenticated, functional, enabled, and target-verified states separately. `registry.resources_runtime` supplies a reviewed plugin-adapter resolver, profile-pinned local overlays, internal bundle rosters, cron/channel/webhook effect envelopes, and authenticated/replay-protected webhook verification. `SQLiteReplayStore` provides a bounded durable replay claim ledger for a root-selected database under an already-private service directory: it commits claims atomically, stores only a digest of the resource/event identity, prunes expired claims, and fails closed without evicting live claims when full. The overlay store provides revisioned compare-and-swap reads/writes, history and soft-delete under a private profile view; it rejects expanded permissions at every directory level. The source pin for native Hermes integration is `NousResearch/hermes-agent@7085fbf7753266fc4943c55ac04926186bc90005`; its Python cron tool is `tools.cronjob_tools.cronjob` and plugin discovery calls `register(ctx)` in the profile runtime. The installer does not import or invoke those APIs from its own process.

Runtime records are generated disabled. Plugin declarations remain pending and emit no native plugin module until an installer-owned loader can inject a trusted runtime context into the actual Hermes `PluginContext`; a registered adapter alone does not prove discovery. MCPs require an enrolled fixed server target and account. Bundle rosters resolve against the pinned closure; the root Hermes topology is kept separate from internal recruitment. `build_selected_resource_effect_handlers` provides a root-only `resource.cron.run` launch backend for enabled, custody-selected cron records. It accepts only the selected profile and a schedule instant that matches the declared timezone/expression, then delegates one bounded launch through the root authority service using the pinned Hermes CLI. A matching timestamp is not proof that the protected scheduler observed a timer event. At the pinned `7085fbf` source, `-p/--profile` selects the profile and top-level `-z/--oneshot PROMPT` runs one shot; this confirms syntax only, not a successful invocation or RB07 child-job admission. A durable bounded job/child-admission ledger is implemented, but the scheduler, protected root event issuers, AuthorityService job/child handlers, process target enrollment, and fresh child-effect grant bridge are not assembled; no schedule can run through RB07 yet. The runtime blocker API therefore reports a missing protected timer issuer and child-admission handler even when the launch target resolves. Channel, webhook delivery and bundle effects remain unavailable pending concrete native/root backends and exact target enrollment; staged declarations are not functional, enabled or target-verified. Webhook receipts never authorize effects; the webhook verifier must be paired with `SQLiteReplayStore` (or another durable bounded implementation) in any root ingress path. Profile overlay values are private, revisioned and compare-and-swap protected; encryption, backup and restore remain separate capabilities.

The contract test `tests/contracts/test_registry_resources_runtime.py` exercises authorization ordering and digest binding, target-spoof denial, root-selected cron delegation and profile-spoof refusal, real overlay adapter registration/invocation and private CAS/tombstones, expanded-parent permission refusal, fixed Hermes routing, webhook signature/replay rejection, and manifest policy guards. Execute it in Linux CI with the project runtime suite; it is not Pi or account acceptance evidence.

Each generated generation is immutable. Stage into a new owned directory, validate files and policy, then atomically replace the active pointer. Failures retain the previous pointer and user data. Authorization must be checked at the actual tool/process/filesystem boundary, including fresh identity lookup for homelab writes; profiles and prompts are not a sandbox.

Hermes alone faces the user. It routes correlated work to bounded internal specialists and receives evidence and dissent before composing a response. Specialists have separate state and cannot bind user channels.
