# Host-issued authority and effect broker

`hermes_installer.authority.client.AuthorityClient` talks to a fixed per-UID AF_UNIX endpoint at `/run/hermes-installer/authority/<uid>.sock`. The directory is root:root mode 0711; each socket is root-owned and accessible only to the matching worker's unique primary GID. `AuthorityClient.for_current_process()` derives the socket filename from the kernel-reported effective UID, never from environment or caller profile labels. The authority service independently obtains `SO_PEERCRED`, maps the UID through protected enrollment, resolves signed source contexts, and signs a context with a short monotonic lease. Empty lineage is `unknown` unless an exact protected profile and purpose rule explicitly classifies it as public. Context fields are correlation data for consumers; callers cannot manufacture them into authority.

The root service assembly surface is `build_authority_service(...)`, which loads the signing key through the root-owned file check, validates that every installed handler has a matching protected rule, and can register the supervised process-handler factory. `serve_authority(...)` starts one socket per enrolled UID and requires a matching unique primary GID. The service unit still needs a protected enrollment loader to supply principal bindings, rules, Authentik secret resolvers, policy, and target-specific provider/MCP/memory/artifact handlers; absent adapters remain unavailable.

An effect grant binds the principal, profile, namespace, UID, purpose, intent, trace, sensitivity, lineage digest, policy revision, capability, exact protected target, policy-resolved recipient, canonical payload digest, retry index, nonce, and expiry. The authority signing key stays in the service and is loaded only from a root-owned regular file with restrictive mode. `verify_effect` verifies and consumes a grant at the host service. Network and process work uses `perform_effect` or a typed verb; the broker verifies and consumes again as part of the actual effect and resolves the target to an enrolled handler. Fixed verbs include provider dispatch, selected MCP channels, memory operations, homelab writes, alarm delivery and supervised process lifecycle. There is no generic URL, shell, credential lookup, or arbitrary HTTP method operation.

Workers must not use direct sockets after requesting a grant. Provider requests, MCP HTTP/stdio calls, memory queue/read/write operations, and process start/read/write/stop use their fixed broker operation. The host broker recomputes the payload digest, checks the signed one-use grant, applies policy again immediately before the handler, bounds the request/response, and consumes the nonce. Disconnect and lease expiry are passed to effect handlers as cancellation. A missing service, grant, handler, target enrollment, or verified kernel feature leaves the operation unavailable.

The optional Codex provider route has one exact `codex://responses` target and `openai:codex` recipient. Its root-owned handler must resolve OAuth solely from protected host custody and send only to the fixed official Responses endpoint; caller URL or token fields are rejected. The route remains unavailable without account enrollment, handler installation and policy approval.

Trusted installer bootstrap uses separate `artifact.fetch` and `package.install` fixed verbs. Callers provide only pinned artifact/package IDs, versions, hashes, and size ceilings. The protected broker registry resolves the official source and staging location; there is no caller URL, package-manager command, or filesystem destination in these APIs. The actual artifact/package handlers must be root-enrolled before bootstrap can use them.

## Authentik System authority

`AuthentikSystemPolicy` performs a fresh TLS-verified GET of `/api/v3/core/users/me/` for every host write or alarm. It matches the returned active username and email against protected principal enrollment and walks every direct group’s `parents` graph (or the documented older singular `parent` form) to completion. It rejects malformed or duplicate references, missing hierarchy fields, cycles, unsupported response shapes, inactive/mismatched subjects, and bounds over 256 groups or 64 levels. A host write also requires the configured target-specific group. Alarm delivery independently resolves the exact enrolled recipient email in a fresh directory query, requires one active exact match, and walks that recipient’s full group hierarchy to verify the configured System and delivery groups. Read errors, incomplete pagination, ambiguous identities, stale membership and unsupported policy fail closed before the handler runs. No membership result is cached.

Authentik’s documented hierarchy makes a user directly assigned to a child group an indirect member of each parent group. The implementation follows those parent references and denies cycles or partial graphs. Authentik’s API `users/me`, group list, and group hierarchy are documented in the [official API reference](https://docs.goauthentik.io/docs/developer-docs/api/reference/core-users-me-retrieve), [groups API reference](https://docs.goauthentik.io/docs/developer-docs/api/reference/core-groups-list), and [group hierarchy documentation](https://docs.goauthentik.io/users-sources/groups/).

## Evidence and limits

The development fixtures exercise actual Unix peer credentials, signed context issuance, exact grant binding, one-use consumption, broker effects, current identity matching, complete nested-group traversal, delivery-recipient lookup, cycle/error/ambiguity denials, and confirmation that denied actions do not call handlers. They do not enroll an Authentik account, prove production token custody, test an ARM64 kernel boundary, or establish native Hermes bypass resistance. No Authentik endpoint, user, target, token reference, or recipient account is enrolled in this repository yet; those capabilities remain unavailable until secure enrollment and native-target evidence exist.
