# Host-issued authority and effect broker

`hermes_installer.authority.client.AuthorityClient` talks to a fixed per-UID AF_UNIX endpoint at `/run/hermes-installer/authority/<uid>.sock`. The directory is root:root mode 0711; each socket is root-owned and accessible only to the matching worker's unique primary GID. `AuthorityClient.for_current_process()` derives the socket filename from the kernel-reported effective UID, never from environment or caller profile labels. The authority service independently obtains `SO_PEERCRED`, maps the UID through protected enrollment, resolves signed source contexts, and signs a context with a short monotonic lease. Empty or unverified source lineage is always `unknown`; purpose strings and profile labels cannot declassify data. Context fields are correlation data for consumers; callers cannot manufacture them into authority.

The installed root entry point is `hermes-installer-authority`. `build_enrolled_authority_service()` loads only `/etc/hermes-installer/authority.json`, `/etc/hermes-installer/authority.key`, and `/etc/hermes-installer/credentials/` after ownership, mode, symlink and size checks; it loads the artifact catalog separately from `/etc/hermes-installer/artifact-catalog.json`. `write_authority_config`, `write_artifact_catalog`, `write_credential`, and `create_authority_signing_key` are root-only enrollment helpers. The configuration contains immutable UIDs/profile/namespace/capability bindings, exact operation/target/recipient rules, an Authentik subject ID plus username/email, group mappings and credential references. It does not accept secret material or arbitrary module paths. MCP HTTP endpoint records must match a reviewed service ID, source ID, transport-binding ID and revision; credentials are opaque root-vault handles. Process, artifact, memory and MCP handlers use fixed reviewed factories. Provider handlers are not registered until a current external account/price/terms/spend admission source is enrolled. A policy grant is not issued when its fixed handler is absent, so unavailable components cannot present a valid-but-unusable grant.

Each context request names a fixed operation and the SHA-256 digest of the exact final canonical payload bytes. The service derives principal, profile, namespace, enrollment generation and native process identity from protected enrollment plus `SO_PEERCRED`; callers cannot pick those claims. `authorize_effect` requires operation, target, recipient and request digest to match that signed context and the protected rule. An effect grant binds the principal, profile, namespace, UID, purpose, intent, trace, sensitivity, lineage digest, policy revision, capability, exact protected target, policy-resolved recipient, canonical payload digest, retry index, nonce, and expiry. The authority signing key stays in the service and is loaded only from a root-owned regular file with restrictive mode. `verify_effect` checks a grant but does not consume it. Network and process work uses `perform_effect` or a typed verb; the broker verifies and consumes the one-use grant at the actual handler boundary. Source receipts are private-only, bound to the native process and parent receipt closure, and consumed with the first effect grant; a repeated receipt is denied. Fixed verbs include provider dispatch, selected MCP channels, memory operations, homelab writes, alarm delivery and supervised process lifecycle. There is no generic URL, shell, credential lookup, or arbitrary HTTP method operation.

Workers must not use direct sockets after requesting a grant. Provider requests, MCP HTTP/stdio calls, memory queue/read/write operations, and process start/read/write/stop use their fixed broker operation. The host broker recomputes the payload digest, checks the signed one-use grant, applies policy again immediately before the handler, bounds the request/response, and consumes the nonce. Disconnect and lease expiry are passed to effect handlers as cancellation. A missing service, grant, handler, target enrollment, or verified kernel feature leaves the operation unavailable.

The optional Codex provider route has one exact `codex://responses` target and `openai:codex` recipient. Its root-owned handler must resolve OAuth solely from protected host custody and send only to the fixed official Responses endpoint; caller URL or token fields are rejected. The route remains unavailable without account enrollment, handler installation and policy approval.

Trusted installer bootstrap uses separate `artifact.fetch` and `package.install` fixed verbs. Callers provide only pinned artifact/package IDs, versions, hashes, and size ceilings. The protected broker registry resolves the official source and staging location; there is no caller URL, package-manager command, or filesystem destination in these APIs. Contexts are bounded to ten minutes; effect leases are operation-scoped (artifact fetch at most 120 seconds, offline package install at most 600 seconds, ordinary effects at most 30 seconds). Long grants still bind one exact canonical payload, one registered target, the current policy revision, and one nonce, and are canceled on disconnect/deadline.

Background memory is a separate root-owned consent path. An enqueue handler asks the authority to create a signed consent bound to the original signed source context, exact profile/namespace/provider, protected owner generation, current policy revision, fixed extract/embed/capture stages, and an expiry of no more than 24 hours. The root queue persists that consent and maintains revocation state. A worker cannot reissue from an expired context directly; the root-side `context_for_job` validates the signature, source binding, active durable consent, owner generation and policy revision, then mints a new short context for exactly one stage. `perform_memory_effect` reauthorizes and consumes a new grant for each stage. If the durable revocation lookup or memory handler is absent, job processing denies. Public-data classification does not follow from empty lineage, purpose names or caller booleans; a separate host-reviewed clearance issuer is still required before public dispatch can be enabled.

## Authentik System authority

`AuthentikSystemPolicy` performs a fresh TLS-verified GET of `/api/v3/core/users/me/` for every authorized effect. It matches the returned active subject ID, username and email against protected principal enrollment and walks every direct group’s `parents` graph (or the documented older singular `parent` form) to completion. It rejects malformed or duplicate references, missing hierarchy fields, cycles, unsupported response shapes, inactive/mismatched subjects, and bounds over 256 groups or 64 levels. A host write also requires the configured target-specific group. Alarm delivery independently resolves the exact enrolled recipient email in a fresh directory query, requires one active exact match, and walks that recipient’s full group hierarchy to verify the configured System and delivery groups. Read errors, incomplete pagination, ambiguous identities, stale membership and unsupported policy fail closed before the handler runs. No membership result is cached.

Authentik’s documented hierarchy makes a user directly assigned to a child group an indirect member of each parent group. The implementation follows those parent references and denies cycles or partial graphs. Authentik’s API `users/me`, group list, and group hierarchy are documented in the [official API reference](https://docs.goauthentik.io/docs/developer-docs/api/reference/core-users-me-retrieve), [groups API reference](https://docs.goauthentik.io/docs/developer-docs/api/reference/core-groups-list), and [group hierarchy documentation](https://docs.goauthentik.io/users-sources/groups/).

## Evidence and limits

The development fixtures exercise actual Unix peer credentials, signed context issuance, exact operation and payload binding, process-bound source receipt use/replay denial, broker effects, current identity matching, complete nested-group traversal, delivery-recipient lookup, cycle/error/ambiguity denials, and confirmation that denied actions do not call handlers. Source capture binds exact bytes observed by the root socket to the kernel peer and host-assigned private/unknown sensitivity; this does not attest that bytes came from a human UI or clear them for public recipients. Static compilation and planning validation are development checks, not Linux broker runtime or target acceptance evidence. They do not enroll an Authentik account, prove production token custody, test an ARM64 kernel boundary, or establish native Hermes bypass resistance. No Authentik endpoint, user, target, token reference, or recipient account is enrolled in this repository yet; those capabilities remain unavailable until secure enrollment and native-target evidence exist. Production service installation, root filesystem custody, account enrollment, per-UID kernel ACLs and real native entrypoint denial still require the reviewed Linux/Pi owner workflow; this development change performs none of those host mutations.

## HI11 paired native provider bridge

The root daemon's `NativeBridgeBroker` is assembled only from a protected `native_bridges` enrollment that uniquely joins the producer and gateway profile/UID/executable generation, an exact provider target and recipient, and the pinned `provider-canonicalizer-v1` digest. `AuthorityClient.prepare_native_event(payload, ...)` captures the complete bounded producer request and returns an opaque, short-lived `NativeEventHandle`; the gateway sends that handle and the bytes it actually observed to `dispatch_native_request`. The root atomically consumes the handle, authenticates both live peers through the managed-process registry, recomputes the enrolled canonical request and digest, and performs the fixed provider operation inside the same IPC request. The handle carries no reusable context, credential, or effect grant; retries require a fresh event handle, and failed dispatches never restore it.

This bridge currently preserves source ancestry as private/unknown and does not issue recipient clearance. Therefore it cannot make a public provider call eligible. A real trusted human/source capture and separately reviewed public-clearance path, current provider account/terms/budget admission, two-process Linux effect tests, and native Hermes boundary evidence remain required. Current development fixtures cover fail-closed denial and single-use behavior; they are not host-kernel or target acceptance evidence.
