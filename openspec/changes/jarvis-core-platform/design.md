### Finite approved email union inside ingress source adoption

`pi_native_core_adopt._source_switch` currently preserves old `allowed_emails` while binding candidate units/new config digest; editing configuration afterward breaks that protected adoption/rollback join. Extend only the existing Root-owned apply transaction with optional `--approved-email-union-stdin` (no addresses in argv). Read one bounded UTF-8 JSON ARRAY from standard input (maximum16384 bytes); no object/paths/commands/credentials or public/browser endpoint. Require the normalized OLD set to be a subset of the supplied explicit approved union; this addition lane cannot remove existing users. Read before any stop/write, do not echo addresses or include them in logs/errors; report count/membership/preservation booleans only. It is the operator's already-authorized bounded configuration input, not a portable grant or signature. Without the flag preserve the exact current allowlist; dry-run/rollback/resume do not silently consume new union input.

Pass the finite validated tuple only to `_source_switch`'s new-config construction; all unrelated configuration fields remain protected current values except already-reviewed source/unit bindings. Persist complete exact prospective `new_gateway_config` bytes in the existing root0700/root0600 ingress backup journal, bound to its existing `new_config_sha256`, alongside the immutable original old config/units. This single closed data field supplies actual resume bytes, not reconstructed approval/authority. Private protected config snapshots may retain emails; no source/argv/browser storage/log copies. Reuse the current finite journal parser/CAS/phase/readback, with explicit backward compatibility: an older journal without the new field can resume only its provably original preserved-email source recipe; it cannot infer/add the newly approved union from the Cloudflare policy or a later caller. Exact post-Core config updates derive from that recorded new config while retaining the union and binding the existing post-Core digest.

Order: verify current/candidate custody→read/validate approved union→construct exact new units/config→fsync protected original/prospective backup and recheck old config/unit CAS→stop owned ingress→atomically replace protected config+units→fresh candidate Inspector/Gateway/core/config readback and normal lifecycle evidence. Mixed phases stay unavailable through existing gates. Resume reads the retained exact new config/digest and same union, with no re-prompt/adhoc old-generation edit. Rollback restores the exact original one-email config/old units/source from immutable backup; do not ask an old loader to accept new three-email data or rewrite that generation. Root separately qualifies current Cloudflare app/policy allowlist and newly issued token behavior; origin switching never changes account-global policy, grants global Extensions/vault access, revives old JWT turns/leases or manufactures added-account acceptance. Existing email-only deployment remains possible without claiming the additional users can log in.

Luna owns only the finite adopter input/config construction/journal compatibility/resume/rollback tests; Root performs actual Pi validation/config/source-cohort activation. Tests must exercise preserving1 and approved1→3 with exact old/new backup bytes/hashes, resume without new input, original1 rollback, unauthorized removal/duplicate/oversize/extra-input refusal BEFORE service effects, changed old CAS/journal/new bytes denial and redacted output. All four current artifacts/full scope/eight OPEN groups remain; no new policy framework.

Hashes cannot prove cognition or review quality. Content delivery is necessary but is not semantic review, and mission result-text review is not required for normal/prior-turn drafts. A subsequent genuine current-master obsidian_promote_reviewed_draft invocation can explicitly express the proposed disposition, while existing owner approval remains the decision to authorize writing.

Draft read producer retains a bounded RootObsidianDraftReadDelivery record: receipt_id, owner_subject_sha256, owner_turn_handle, draft_id/content_sha256, origin_record_sha256, current master source_generation_sha256, actual observed read-call handle/tool_call_id/arguments_sha256, returned content byte length/digest, complete flag/coverage and delivered_at. Complete is derived only from actual full exact stored Markdown returned through the admitted read; oversized/truncated/chunk-incomplete output remains incomplete. This is DATA about delivery under the prior read admission, not a renewable lease. A pending promotion in that same still-current owner turn can reference it even after the earlier read-call lease elapsed; new/expired owner turns need a fresh complete read. Root independently verifies digest/origin/current draft at proposal time.

Promotion's closed schema adds required review_disposition='approve'; optional review_rationale is plain bounded text <=512 characters, never permission or hidden instructions. The existing exact draft_id/expected_draft_sha256/destination/expected_base_sha256 fields stay required. Reject/revise is not a promotion call and leaves the draft pending for editing/review. Root derives a typed RootJarvisDraftReviewProposal only from the actual current-master observed provider invocation after matching same-current-owner-turn complete read delivery; no caller-created assurance Boolean or generic model statement. Closed fields: proposal_id, owner_subject_sha256, owner_turn_handle, draft_id, content_sha256, destination, expected_base_sha256|null, disposition, rationale|null, observed_promotion_call_handle/tool_call_id/arguments_sha256, master source_generation_sha256, read_delivery_receipt_id/read_delivery_sha256, origin_record_sha256, created_at and original owner/call deadline. Store proposal separate from read and owner FinalEffectPermit; proposal means “Jarvis proposed approval after exact content delivery,” not verified mental review or authorized mutation.

Existing final-effect approval preview shows that exact proposed disposition, bounded rationale and note/digest/destination/base consequence. review_digest/canonical arguments and current root permit bind the new schema unchanged, with current master source/owner and one-use approval. Obtain the single short promotion scope/origin proof after valid permit while original observed call/owner still current, then recheck proposal/read/content/base/CAS at write. A changed draft/destination/base/source, incomplete/foreign/prior-owner-turn read, missing genuine proposal or expired permit denies without automatic repeat. There is no mandatory mission wrapper, additional general review service or claim of proving a model's internal thought.

### Explicit origin completion and bounded retained history

Only an explicit root completion observation after actual native promotion and independent note/private-record post-write readback may retire an active origin. Bind completion to current master observed call/permit digest, exact origin/draft/content/destination/base, verified final note digest, promoted draft state and completion time. A tool return string, sidecar age, disappearance or passive file scan is not completion. Uncertain/conflicting write leaves active origin pending; do not reclaim its capacity or rerun the effect automatically.

Before removing a completed origin from the active pending index, atomically persist its original root producer attribution plus proposal/owner-approval/result references in a root-owned 0600 archive segment under the same verified journal directory, fsync and read back the exact archive digest. Then write a bounded completed tombstone/index reference (draft ID, origin_record_sha256, archive record ID/digest, final destination/note digest, completed time/state) and reclaim active capacity. Crash recovery retains active or verified archived attribution and never silently loses a pending origin. A completed ID cannot be recorded again as another pending origin or promoted twice. History is DATA; restoring/read-inspecting it cannot resurrect grants. History storage has an explicit bound/next archival step; reaching it pends new completion/registration or requires a separately deliberate archive action, never evicts learned data or original provenance silently.

Promoted private draft records may mirror original source/execution/mission and root origin-record/archive IDs/digests for inspection. A UID1000 private-file mirror alone is not trusted root provenance, even if its fields are called sealed. Reconstruction after active-index compaction must resolve the retained root archive and verify its exact record/digest plus actual draft/note bytes under current owner registration. No new signing-key framework is needed; verified root archive custody is the authority for historical attribution. If archive is missing/corrupt, label provenance unknown and preserve notes; never manufacture it from the private record. Existing active index cap excludes successfully archived completed records but still counts uncompleted/uncertain origins. Resources/Obsidian owner implements producer/completion/resolver atomic states; ROOT integrates shared custody/pins and Pi tests.
