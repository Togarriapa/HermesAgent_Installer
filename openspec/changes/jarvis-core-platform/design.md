# Design

Use official pinned Hermes headless core independently from Electron. The source supplies hermes serve REST/WS and a separate authenticated API-server session/chat SSE/run interface; neither is a family-safe public proxy. Phase 1 uses existing `hermes serve` → `hermes_cli.web_server` → private authenticated `/api/ws` → `tui_gateway.ws`, with a thin server-side JSON-RPC client. Do not start a second API-server gateway platform: `/api/sessions/{id}/chat/stream` belongs to that distinct listener and is not the serve contract. Pin and verify `session.create`, `prompt.submit`, `session.history`/replay and `session.interrupt` request/event schemas from this exact source; server-derived subject → conversation → runtime-session ownership is mandatory. Browser receives finite BFF routes only, never raw RPC, token, profile/system parameters or arbitrary methods. Later rich capabilities extend this adapter one verified contract at a time. Retain local credential and process/home ownership; no invented management adapter is accepted.

Phase 1 adds validated core component selection and a concrete adapter DAG, separates graphical preflight, safely adopts current home/Codex auth, stages only owned official upstream bytes/PM Python3.14, and independently starts a journaled owned service. First prove health, configured-account harmless chat, restart and rollback; only then disable owned Desktop/display launch. Preserve installed recovery artifacts and WIP; do not delete user data or other services. Official installer optional browser/computer-use selection must be explicit, never lazy installed.

Phase 2 uses the exploration capability matrix as a live port ledger. Bots backend DM continuity differs from renderer-local group orchestration and relay; implement durable server state/worker before availability. Rich run events/approvals and scoped browser/artifact adapters require actual contracts and failure proof. Retain pending methods rather than mocks. An initial capability unlocks phase 3; further ports continue incrementally.

Phase 3 carries forward v265 finite BFF and mobile accessibility but removes native owner Desktop as product requirement. Preserve the owned hostname/Access OTP/binding and current safe cloud resources. Core UI must have its own verified backend custody, not relabel an Xpra/native inspection proof. Family permissions are explicit; no shared global tool/memory isolation promise. Jarvis uses original restrained dark/cyan visual assets, keyboard access and reduced motion; polish follows functionality.

Phase 4 imports full Resources via actual native core discovery/dispatch with original identities and budgets; phase 5 audits full scope and actual Pi recovery/security/capability evidence. HA remains deferred. Existing native proposals are historical/superseded for active presentation only. Validation is Pi-only; this planning commit performs no local validation or deployment.

Immediate core migration recipe: reuse the currently proven official PM runtime after exact executable/source/lock verification, with the unchanged selected home and Codex credential references. A concrete owned service adapter runs only the verified official `hermes serve --host 127.0.0.1 --port <owned validated loopback port>` under the selected unprivileged owner with fixed HOME/HERMES_HOME and sanitized environment; the port comes from the protected owned configuration, not browser input. The adapter implements actual install/resume/recovery and systemd unit readback, private authenticated health/session/chat/interrupt and restart checks. It does not expose a caller command/callback. If the existing managed path cannot retain this service, implement this finite owned recipe directly rather than a placeholder. Reversible retirement stops/disables only journal-identified owned Desktop/Xpra units, preserving AppDir, backups and state. Existing-target migration success and clean fresh-install acceptance are separate evidence; fresh install remains OPEN until tested.
