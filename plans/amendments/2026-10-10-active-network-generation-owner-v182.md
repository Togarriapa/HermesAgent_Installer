## Complete revalidation and reload boundaries

Before issuance, immediately before helper spawn, after stopped helper ready observation and immediately before same-PID release/exec, and at every use of any retained active network admission, owner must: (1) verify held release and current root controller actor/key; (2) resolve current active publication and compare exact pointer/receipt/selection/descriptor/claim, service generation and enrollment catalog; (3) join complete output bytes by actual compiler member receipt and verify active protected enrollment loaded through existing protected loader, exact row digests and process/principal/profile generation; (4) call attached runtime choice registry.resolve_current_adopted_choice(handle,'native-policy-preparation',current_publication), check signed source/adoption/epochs plus fresh durable revocation, policy/principal/namespace bindings; (5) reopen/verify the exact root journal directory by catalog/current generation, nofollow FD/inode/root owner/mode and check key/source-store custody; (6) reread current publication/enrollment pointer after joins and deny on any concurrent CAS transition. Root publication/CAS lock and journal lock must cover final admission/release decision or an equivalent concrete serialization owned by the publisher and manager; read-before/read-after alone must not claim atomic immunity to a later revoke. Revocation commit invalidates owner projections and causes manager cancellation/cleanup before acknowledging continued worker admission; no callback that returns a hardcoded boolean.

This does not renew external account/Authentik checks or grant host authority: effects still need their own current authorization. Reconfiguration/revocation, release/code/key replacement, actor death/restart, journal inode change, active pointer/CAS mismatch, publication prepared state, profile generation change or runtime close invalidates every projection. Service reload explicitly closes helper registry/managers (cancel stopped/running children, bounded verified cleanup), closes generation owner, then choice verifier/actor/release custody in dependency order; a new daemon runtime constructs new owner/projections from current protected state. No persisted projection is accepted after restart. Original signed choice journal/adoption can be freshly resolved; historical process-local seal/boot_epoch cannot.
