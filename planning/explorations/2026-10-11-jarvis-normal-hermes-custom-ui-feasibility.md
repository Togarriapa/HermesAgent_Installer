# Normal Hermes engine and custom Jarvis UI: source-backed exploration

Exploration only, requested 2026-10-11. No new amendment, implementation tasks, migration, runtime change or acceptance claim. v265 practical mobile/family work remains the immediate priority; all original Resources/native/model/Coral/plugin/account scope stays OPEN.

## Feasibility and recommendation

Yes: the official Hermes engine can run without Electron. At pinned `NousResearch/hermes-agent@7085fbf7753266fc4943c55ac04926186bc90005`, `apps/desktop/electron/backend-command.ts:3,17` builds `hermes serve --host 127.0.0.1 --port 0`. `hermes_cli/subcommands/dashboard.py:1,48,68` defines serve as the same headless backend used by Desktop, skipping browser UI build. `hermes_cli/web_server.py:1591` assembles that backend. Electron is a client/process manager, not the sole owner of agent intelligence.

Recommend a custom responsive Jarvis web client through a finite authenticated server-side adapter to this existing engine, while retaining the working native Desktop fallback. Do not uninstall Desktop or migrate data first. Use the already verified selected Hermes runtime/home/model/provider and one actual memory owner; do not launch an accidental second divergent agent stack. If the current served backend is reused, bind its actual authenticated REST/JSON-RPC lifecycle. If selecting the separate official API-server platform, verify its activation/configuration and shared-state semantics before changing v265's backend adapter. Neither route is a generic proxy.

The Desktop renderer cannot simply be published unchanged: `src/api/client.ts:126,193` calls `window.hermesDesktop.api`, supplied by `electron/preload.ts:28`; `src/global.d.ts` describes native capabilities. Its complete API surface includes configuration, filesystem, model installation, OAuth and process management. A browser replacement is a new client, with feature-by-feature adapters and validation, not an Electron bridge shim or full backend exposed to the Internet.

## Backend choices and minimum safe boundary

1. **Existing `hermes serve` engine** gives the broadest Desktop-backend continuity. Its REST routers and `/api/ws` (`tui_gateway/ws.py`) run in Python without Electron; `tui_gateway/entry.py:273` also supplies stdio JSON-RPC for local clients. Bots profile/relay handlers are registered through `tui_gateway/server.py:3656..3676`. This confirms source availability, not a supported public multi-user RPC endpoint. A local adapter must allow exact methods/schema and resolve actual session/profile owner before invoking them. Never expose `cli.exec`, `shell.exec`, generic `command.dispatch`, raw profile IDs or backend URLs.
2. **Official API-server platform** (`gateway/platforms/api_server.py`) supplies authenticated conversation/run REST+SSE with API_SERVER_KEY, session keys and run limits, suited to v265. It is narrower than Desktop's full backend: advertised flags include `admin_config_rw=False`, `jobs_admin=False`, `memory_write_api=False`, `audio_api=False`. Full capability parity cannot be inferred from chat API support. Activation, actual current model/provider/home, concurrency and memory behavior need a real test.
3. **Desktop renderer transplant** would require replacing many `hermesDesktop` IPC/native capabilities and reviewing management routes. It is more work and risk than an incremental original client; not recommended for the immediate MVP.

Keep Access binding/OTP, JWT-before-bytes, verified owned origin peer, CSRF/origin controls and existing bounded stream heartbeat/revocation. Backend credential stays in server-owned protected reference. Family and owner-admin routes must have separate explicit capability sets. Owner-admin adapters expose individual safe functions, not the upstream router wholesale. Existing native fallback permits advanced owner work while those adapters are incrementally proved.

## Family trust boundary

Per-principal chat/session ownership is essential but only protects the UI/API transcript boundary. It does not isolate agent execution, filesystem, tool credentials, global memory, connectors or model context. A shared service can access whatever its UID and tools permit. Do not call HERMES_HOME/profile names a sandbox. Two practical options remain: restrict family capabilities to verified conversation/private-scope operations, or add actual separate per-principal execution/data custody and tool grants before offering private agent tools/memory. The latter is a later security implementation, not something this exploration has proved.

An API server session-key header is a continuity/memory scope feature, not an externally trusted principal. The adapter generates/maps it server-side and enforces ownership on read/send/stream/stop/reconnect. Unknown/deferred isolation means the affected feature stays unavailable. Roster expansion needs actual approved identities; current owner-only Access is not family admission. HA remains a separate future machine principal/channel, explicitly deferred, not a browser token reuse. Sharing backend capacity with the screen is feasible in source but actual concurrent service/credential behavior must be tested.

## Small phased path, without committing a migration

- **First: finish v265.** Mobile keyboard, real streaming chat/stop/history, correct Jarvis persona, two approved independent conversations, native fallback, ownership/auth/revocation/restart and honest busy states. No parity requirement before a useful chat exists.
- **Then: owner features in small groups.** Read-only capabilities/status, skills/Bots inventory and own-session progress/approvals; followed by individually reviewed owner configuration or job actions. Each has a matrix row, exact adapter and positive/negative target evidence. Existing Desktop remains the fallback until replacement proves the same feature.
- **Then: useful rich interaction and visual polish.** Owned attachments/artifact preview, optional proven voice, restrained animations/hud-like styling and reduced motion. Avoid model/provider spend or graphics that hide state/errors.
- **Only later decide Desktop replacement.** Compare real supported feature matrix, stability, accessibility and owner workflows. Preserve native binary/state/settings/recovery and every original obligation; remove reliance only after explicit verified replacement, not because a polished chat demo exists.

## Evidence limits and next decisions

Audit used only pinned local source `/private/tmp/hermes-agent-source-pinned`; no engine processes, physical Pi, Cloudflare, accounts, messages or downloads were changed. ## Android companion and wake-word feasibility (additional exploration)

A native Android companion is a plausible later route to a phone-level Jarvis assistant; the web/PWA chat remains the first practical deliverable and push-to-talk fallback. Android documents a user-selected `VoiceInteractionService` maintained for background voice interaction, and a selectable `ROLE_ASSISTANT`. That supports investigating native assistant integration, not promising it works on every OEM/locked device. [VoiceInteractionService](https://developer.android.com/reference/android/service/voice/VoiceInteractionService), [assistant role](https://developer.android.com/reference/android/app/role/RoleManager#ROLE_ASSISTANT).

Android14+ restricts starting microphone foreground services from background while-in-use permission contexts; documented exemptions include apps providing VoiceInteractionService. Explicit role selection/microphone consent and actual device/version behavior still matter. A browser background tab cannot substitute for a qualified native assistant service. [Foreground-service restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start).

AOSP Android14 hotword detector creation is system-API/permission constrained; DSP availability, enrollment and OEM integration are separate from ordinary third-party microphone access. Do not promise generic hardware always-on detection, arbitrary locked-screen actions or bypass restrictions. [AOSP VoiceInteractionService source](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android14-release/core/java/android/service/voice/VoiceInteractionService.java).

A software local keyword detector is another candidate: sherpa-onnx documents keyword spotting and Android samples. Investigate its selected model license, footprint, device ABI, battery use and false activation rate before choosing it; no model download, purchase or qualification occurred here. [Keyword spotting](https://k2-fsa.github.io/sherpa/onnx/kws/index.html), [Android examples](https://github.com/k2-fsa/sherpa-onnx/blob/master/android/README.md).

Proposed later flow, not implementation: explicit Android assistant role + microphone opt-in -> lightweight local wake detector -> bounded STT -> same principal-owned authenticated Jarvis conversation API -> TTS. Visible microphone indicator/mute, intentional recording start/stop, no continuous audio upload and minimal local buffer retention are prerequisites. Sensitive private data/actions while locked require unlock; never grant house/host actions from a wake word alone. Per-device revocable authentication must be designed separately: no global Cloudflare management token, shared backend API key or browser OTP bypass in the app. Secure OAuth/device enrollment/M2M transport is currently unimplemented and cannot be assumed from working browser Access.

Qualification needs the actual phone model/Android version and user-selected assistant support, then wake/screen-off/lock/reboot, battery saver, OEM process killing, Bluetooth/headset, incoming-call interruption, false positives, permission withdrawal, token revocation and offline/fallback tests. A PWA alone is not a reliable always-on locked-screen assistant. Keep accessible push-to-talk/text working even when assistant-role/hotword support is unavailable. Sequence remains practical v265 mobile/family chat first, optional voice next, native Android companion only after a small device-specific feasibility spike. No new amendment/app implementation or phone mutation is authorized by this exploration report.
